# WinSim 结果汇总（W0–W8）

> 设计：[results/winsim/WINSIM.md](WINSIM.md)　代码：`winsim/index.html` + `winsim_w0..w8.py`
> 环境：纯 HTML/JS 桌面壳（真 Chromium 渲染），seeded RNG + 虚拟时钟，无外部依赖
> 目的：给"像素型 CUA"造一个**可控、可重放、有外部真值、可注入故障**的评测/训练床

---

## 0. 一句话

> WinSim 把"结构通道（a11y/DOM 白送框）"与"像素通道（自己看、自己检测）"放进
> **同一个可交互桌面**里对照，量出了 sim-to-real 的真实落差：
> **next-action 命中 1.00（结构）→ 0.26（端到端像素）**，且 OOD 直接归零。

## 2. 核心对照：从"白送结构"到自己看

| 形态 | in-domain | OOD-theme | OOD-app |
|---|---|---|---|
| 结构通道（uia 白送框） | **1.000** | 1.000 | 0.500 |
| 像素选择（给定框，W6） | **1.000** | 0.587 | 0.159 |
| 自己检测（W7/W9 recall） | 0.412 | 0.208 | — |
| **端到端（W8 独立训练）** | 0.260 | 0.075 | 0.000 |
| **端到端（W10 联合训练）** | **0.790** | **0.500** | **0.000** |

三条可复现的结论：

1. **结构通道是"作弊"，但它是必要参照**：白送框把最难的一步（检测）拿掉了。
2. **像素的失败首先是"检测"，不是"选择"**：给定框时像素选择满分（1.000），
   自己检测只剩 0.412 → **"把结构从像素里恢复"才是瓶颈**（与 P7/P8 一致）。
   **W10 修正**：把选择器从"oracle 框"改训到"检测框"后，端到端 in-domain
   从 0.426 → **0.790**（+0.365）——此前的一大截是**训练/推理分布不匹配**（实现问题），
   不是方法极限。剩下的 0.21 差距才是检测质量 + 真实接地难度。
3. **OOD 是压垮像素的第二刀**：未见主题 0.587→0.500、未见应用 0.159→0.000；
   而结构通道对主题**完全不变**（drop 0）。

### 2.1 索引化动作空间（W11，借鉴 [browser-use/jev-ultrafast](https://github.com/browser-use/jev-ultrafast)）

jev 的设计：观测 → element table；决策 = `(operation, target)`，且**只提供兼容组合**；
一次前向出两个 head；小 LLM 只在 `TYPE_TEXT` 时生成文本。

我们在 WinSim 里实现并消融（新增 **rename** 任务，让 `TYPE_TEXT` 真实存在）：

| split | op+target 无掩码 | **op+target 有掩码** |
|---|---|---|
| in-domain | 0.868 | **0.934** |
| OOD-theme | 0.889 | **0.944** |
| OOD-app | 0.000 | 0.000 |

- **兼容掩码有净收益**（+0.066 / +0.055）：与 jev 的设计主张一致。
- **op 轴是必要的**：`TYPE_TEXT` 步在"只预测目标元素"的旧臂里**无法表达**（旧臂无 op）。
- OOD-app 仍 0：未见应用/操作 → 覆盖问题对结构化策略同样成立（与 W5 一致）。

### 2.2 混合臂（W12）：结构可用则用结构，不可用回退像素

新增 **canvas 应用**：控件画在 `<canvas>` 上 → **不进 `elements()`**，只能靠像素。
任务族 = DOM（move/delete/toggle）+ canvas（点画布上的目标色块）。三条臂同一批样本：

| arm | DOM | canvas | overall |
|---|---|---|---|
| struct-only | **1.000** | 0.500 | 0.750 |
| pixel-only（检测+选择） | 0.402 | **0.607** | 0.505 |
| **hybrid**（`step_name ∈ elements()` → struct，否则 → pixel） | **1.000** | **0.607** | **0.804** |

- **hybrid 严格优于两条单臂**：DOM 上拿到 struct 的 1.000，canvas 上拿到 pixel 的 0.607。
- 这正是 [jev-ultrafast](https://github.com/browser-use/jev-ultrafast) 自己列出的局限
  （shadow DOM / canvas / frames）所在的区域——**结构不可得时只能回退像素，而像素只有 0.6**。
- 工程要点：**struct 必须训在"它将被路由到的所有步"上**（否则连"打开 Canvas 应用"这一步都会失手）；
  路由必须按**本步**目标名判断，而不是任务名。

## 4. 工程上踩过的真坑（可复现性记录）

| 坑 | 现象 | 修复 |
|---|---|---|
| `render()` 只清 `.win` | 弹窗遮罩/loading 残留 → OK 反复出现、双方卡死 | 清 `.win/.dialog-overlay/.loading` |
| 每 instance 启一个浏览器（420 次） | 截图失败（资源耗尽） | 单页复用 + `reset()` |
| 路径语义 `["Home"]` | `resolve()` undefined | root = 空路径 |
| BC 门共享指令嵌入 | 训练塌缩（train acc 0.23） | 门只吃 `stale`，选 slot 与是否重观察解耦 |
| 数据集 off-by-one | 动作后 obs 配动作前 action（116/150 错位） | 记录**动作前**观察 |
| 检测器塌成常数 | objmax 恒 0.37、recall 0.09 | sigma 1→2 cells、size 权重 5→1、w24→32、thr 0.3→0.2 → 0.31 |

## 5. 局限（不要过度解读）

- **检测器是小型 CenterNet-lite**：W9 试了更强头（stride 2）+ 修尺寸监督，
  in-domain e2e 0.260 → 0.290、recall 0.307 → 0.412。**W10 进一步证明**：
  真正的主因是**选择器训在 oracle 框上**（分布不匹配）——改训在检测框上后
  e2e 到 **0.790**。所以 W9 的"方法极限"判断**被 W10 推翻**，应表述为
  "实现（分布不匹配）占大头，检测质量+接地难度是剩余部分"。
- **运行间波动**：同一组合（oracle 框选择器）在 W9 报 0.290、在 W10 报 0.426
  ——GPU 非确定性导致 ±0.13 的抖动；W10 的结论是**同一次运行内**的对照（同一检测器），
  因此 +0.365 仍成立。
- **尺寸监督的坑（与 P9 同源）**：尺寸标签若只在中心 cell 非零、而 objectness 正区域
  是整片高斯，size head 会被压向 0（实测 ~3.6px）→ 检测被 min-size 全部滤掉。
  修法：尺寸标签铺满高斯正区域。（P9 的 per-R 训练踩过同一个坑。）- **检测与选择各自独立训练**：没有联合微调；分布不匹配（检测框 vs oracle 框）。
- **任务是合成的、规模小**（3 应用、4 任务类型）；未做长 horizon。
- **像素通道此前被"完美候选框"优惠**（W6），真正的端到端只有 W7/W8。
- WinSim 不是真 Windows：不含 OS chrome、跨进程、真实应用；它是**可控中间层**。

---

## 6. 结论

> **1.00 → 0.26**。这个落差不是渲染问题（headless vs headed 已证可忽略），
> 不是动作语义问题（双向、不确定），而是**"信息从哪来"**的问题：
> 结构白送 vs 从像素恢复。并且这个落差在**分布外**（新主题/新应用）会放大到归零。
>
> 对训练的直接含义：像素型 CUA 必须做**端到端**（含检测）+ **站点/应用级 held-out**，
> 否则会在 in-domain 上自欺（W6 给定框时 1.000）。
