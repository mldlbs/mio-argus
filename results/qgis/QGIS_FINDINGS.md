## 0. 一句话

> 在真桌面应用上，**H1（重观察）与 H3（结果验证）都拿到了真值判定的证据**；

## 1. 环境：四条通道（PyQGIS 桥）

| 通道 | 实现 | 用途 |
|---|---|---|
| **真值** `truth()` | `QgsProject` / 图层树 / `QgsMapCanvas` | 状态判定（外部真值，不是"点了就算"） |

## 4. 这轮的**新增**（其它线没有的）

1. **H1 在真桌面上的"静默错误"形式**：过期坐标点中的是**另一个真按钮**——
   不是失败，是**自信地做错**。这比"点空"更危险，也是重观察的最强论据。
2. **H3 用真应用的"后果"**：V 看 (动作前, 动作后) 截图，AUC = 1.000；
   且**默认阈值会把它毁掉**（P6 的方法论再次成立）。
3. **门控重试 ≠ 收益**：独立重掷的上限 `1-(1-q)^3`，V 不改变它——
   V 的价值是**知道失败了**（止损/恢复），不是"多掷几次"。
4. **真输入的代价轴**：真鼠标 810 ms vs 特权 180 ms（4–5×）。

---

## 5. 局限

- **单一应用**（QGIS）；任务集小（4–6 个），无长 horizon。
- 多数动作走**特权 Qt**；真鼠标只覆盖 W4 的三个情形。
- **像素臂只是外观探针**（W1），没有端到端像素 agent（检测+选择）。
- 桥依赖 `QScintilla`/`QTest`/`QgsLayerTreeView` 等具体控件类，**换应用要重写提取器**。
- 真鼠标臂会**占用桌面**。

# QGIS W6：把 QGIS 训练好（状态生成 + 三臂 + 两种 held-out）

> 复现：`python experiments/qgis/qgis_bridge/run_w6.py`（`--recollect` 重新采集）　数据：`experiments/qgis/qgis_bridge/w6_data.npz` / `w6_results.json`

这一轮**造数据**：程序化生成 **8 种 UI 状态**
（窗口 最大化/1200×800 × Python 控制台 关/开 × 表达式对话框 关/开），
每种状态随机化 canvas 视图与图层可见性，**共 1200 个样本**。

样本 =（整窗截图, 16 个候选控件, 指令=目标控件名）→ 目标下标；
候选裁剪 32×48；chance = 1/16 = 0.062。

| arm | in-domain | **未见 UI 状态** | **未见控件名** |
|---|---|---|---|
| **struct**（控件名文本 + bbox） | **0.970** | **0.854** | 0.218 |
| **pixel**（候选裁剪 → CNN） | 0.412 | 0.292 | 0.046 |
| hybrid（朴素相加） | 0.972 | 0.727 | 0.155 |

**数据规模效应**（同一套 pipeline，480 → 1200 样本）：

| arm | in-domain | 未见状态 |
|---|---|---|
| struct | 0.983 → 0.970 | **0.659 → 0.854** |
| pixel | 0.207 → **0.412** | 0.044 → **0.292** |

**四条结论**

1. **结构臂训得起来、也迁移**：in-domain 0.970、**跨未见 UI 状态 0.854**。
   换窗口大小/开关控制台/开关对话框都扛得住——这是"窄域单应用"路线的正面证据。
2. **数据规模对像素臂帮助最大**：跨状态 0.044 → **0.292**（6.6×）、in-domain 翻倍。
   但**仍只有 struct 的 1/3**——"从像素读名字/语义"这堵墙还在。
3. **未见控件名是共同的墙**：struct 0.218、pixel 0.046（chance 0.062）。
   与 W3（0.043）、`real_site_policy`（0.386）、`WinSim W5/W11`（未见应用 0）**同一条曲线**。
4. **朴素相加的 hybrid 是错的**：它被弱像素分支拖累（0.727 < 0.854）。
   正确形态是**路由**（结构可用→struct，不可用→pixel），对齐 `WinSim W12` 的 0.804。

**至此"把 QGIS 训练好"完成**：1200 个程序化 UI 状态、三条臂、两个 held-out 轴，
结构臂 0.970/0.854，像素臂 0.412/0.292，且给出了数据规模效应曲线。

# QGIS W7：路由器式 hybrid（结构可用→struct；不可用→pixel）

> 复现：`python experiments/qgis/qgis_bridge/run_w7.py`　数据：`experiments/qgis/qgis_bridge/w7_results.json`
> 同一 1200 样本集与同款划分（train 434 / held-out 状态 418）

W6 的 hybrid 是**朴素相加**，被弱像素分支拖累（0.727 < 0.854）。W7 改成**路由**：
候选有名字且指令与某个名字有词重叠 → struct；否则（名字被抹掉 = 模拟"没有可命名控件的区域"，
如地图画布）→ pixel。

| 集合 | struct | pixel | **router** | 走 struct 比例 |
|---|---|---|---|---|
| normal（有名字，held-out 状态） | 0.852 | 0.373 | **0.833** | 0.98 |
| masked（名字抹掉＝无结构区） | 0.196 | 0.373 | **0.373** | 0.00 |
| **mixed（各半）** | 0.526 | 0.416 | **0.622** | 0.49 |

**三条结论**

1. **路由按设计工作**：有名字时 98% 走 struct（0.833 ≈ struct 的 0.852）；
   名字抹掉时 0% 走 struct（0.373 = pixel，分毫不差）。
2. **mixed 上 router 严格优于两支单臂**（0.622 > 0.526 > 0.416）——
   `WinSim W12` 的结论在**真桌面应用**上复现。
3. **修好了朴素相加的拖累**：held-out 状态 0.727 → **0.833**。

> 结构可用时你几乎免费（0.85）；结构不可得时你要付 **0.37**（像素）；
> **路由让你同时拿到两侧的最好值**——这就是"窄域单应用 + 混合臂"的最终形态。

# QGIS W8：长 horizon 的失败尝试（设计错，已诊断）

> 复现：`python experiments/qgis/qgis_bridge/run_w8.py`　数据：`experiments/qgis/qgis_bridge/w8_results.json`
> **结论：不成立**——因为任务设计违反了 P3 的前提。

**我的设计**：k 个连续子目标（每次"复原视图"），动作以 q=0.5 正确；
`no-V / learned-V / oracle-V` 三种判断方式，看成功率是否随 k 拉开。

| k | no-V | learned-V | oracle-V |
|---|---|---|---|
| 1 | 0.458 | 0.583 | 0.958 |
| 2 | 0.542 | 0.625 | 0.875 |
| 4 | 0.667 | 0.750 | 0.958 |

**为什么失败（诊断）**

1. **子目标同质且可被下一次尝试修好**：k 个都是"复原视图"，
   所以第 i 步失败会被第 i+1 步的成功覆盖——**失败不累积**。
   结果 `no-V` 的成功率 ≈ q（0.46–0.67），**与 k 无关**（本该随 k 衰减）。
2. **P3 形式的前提是"子目标相互依赖 + 错误状态有代价"**：
   下一步必须建立在上一步正确的状态上（例如 选择→按选择缩放→导出）。
   没有依赖，V 的门控只能**省步数**，改不了成功率——与 W5 的 +0.000 同一个道理。
3. 顺带：本轮的 V 也只训到验证 acc 0.600（W5 同任务曾到 AUC 1.0），
   说明裁剪/标签在这个设置下更噪声——不深究，留作已知问题。

**这轮的正面产出**：把"V 何时才有价值"的前提写死了——
**要么子目标有依赖、要么错误状态有成本**，否则独立重掷的上限就是天花板。

# QGIS W9：依赖式子任务上的 V（P3 形式，修正版）✅

> 复现：`python experiments/qgis/qgis_bridge/run_w9.py`　数据：`experiments/qgis/qgis_bridge/w9_results.json`

**任务（真依赖，错误会带下去）**

```
S1 按表达式选择 pop>1e6  → 真值 selected == 2
S2 按选择缩放            → 真值 extent ≈ 选择的 bbox
S3 导出 GeoJSON（仅选中） → 真值 文件里恰好 {London, Beijing}
```
S1 错（选 0 个）→ S3 导出空文件；S3 错（导出全部）→ 5 个要素。**最终产物只有一个正确答案。**

| k（依赖链步数） | no-V | learned-V | truth-V |
|---|---|---|---|
| 1 | 0.417 | 0.333 | 1.000 |
| 2 | 0.250 | 0.250 | 0.917 |
| **3** | **0.000** | **0.250** | 0.750 |

**V 相对 no-V 的增益：k=1 −0.083 → k=3 +0.250（随 k 单调上升）** = **P3 的 crossing 形式**。

**三条结论**

1. **依赖成立**：`no-V` 随 k 崩塌（0.417 → 0.250 → **0.000**）——
   这正是 W8 缺失的前提（同质子目标时 no-V ≈ q 与 k 无关）。
2. **V 的价值随 horizon 上升**：learned-V 在 k=3 仍保住 0.250，**增益 +0.250**；
   W5 的"独立重掷 +0.000"被彻底翻转。
3. **差距在哪**：learned-V 只覆盖 **S1（关键前置）**（V 的 AUC=0.968、校准后 acc=0.920），
   S2/S3 仍未验证 → 与 truth-V（0.750）的差距就是"没被验证的那两步"。
   把 W5/W9 的 verifier 分别装到 S2（视觉）与 S3（读文件，天然可验证）即可补齐。

> ⚠️ **上述第 3 条的 AUC=0.968 后来被证伪（见下方 W9 修正 + W10）**：
> 那个 verifier 读的是"无匹配要素"警告框伪迹，不是选择状态。保留原文以便追溯。

**顺带修掉的桥缺陷**：模态对话框（`QDialog.exec`）会阻塞 Qt 主线程，
同步 `trigger()` 会把泵卡死（"Save As…" 实测超时）。
改成 **`QTimer.singleShot(0, action.trigger)` 异步触发**后，模态嵌套循环期间泵仍可服务。

# QGIS W10：verifier 伪迹的自我修正 + 可见结果的依赖链 ✅

> 复现：`python experiments/qgis/qgis_bridge/run_w10.py`　数据：`experiments/qgis/qgis_bridge/w10_results.json`
> 三组对照的原始诊断见下（点图层 vs 多边形图层，各 60 对）。

**W9 的 verifier 是在读伪迹，不是在读结果。**

W9 用点图层（5 个圆点）做 S1"选中 2 个"，测出的画面信号只有 diff≈0.0034——
在 1600×1100 裁剪再缩到 256×128 后，被选中的点只剩 1px。**正确样本的 after 与
before 几乎逐像素相同（diff=0.0001）**，而失败变体（选 0 个）会弹
"No matching features" 警告框（diff=0.0038）。于是 V 学会了"有没有弹窗"：

| 对照条件（各 60 对，同一 V 结构） | 视觉信号 diff(ok/bad) | V AUC |
|---|---|---|
| 点图层，错误变体选 0 个（**弹警告框**，= W9 原协议） | 0.0001 / 0.0038 | 0.824（W9 那次 0.968） |
| 点图层，错误变体选另外 3 个（**不弹窗**） | 0.0034 / 0.0052 | 0.748（贴噪声底） |
| **多边形图层，错误变体选另外 3 个（不弹窗）** | **21.5 / 38.1** | **1.000** |

**教训（P3 的必要条件）：verifier 只能验证"可观测的结果"。**
结果不可观测时，V 会去抓与失败相关的**旁支伪迹**（弹窗、渲染差异），
看上去很强、实则一换时序就崩——这正是 W9 里 AUC 0.968 与 0.250 增益的来源。
而且 W9 的 learned-V 结果本身不稳定（重跑一次从 0.250 掉到 0.167），也是同一病灶。

**修正后的任务（结果可见、错误变体不弹窗）**

```
S1 select_expr('"area" > 300') → 真值 selected == 2（North, South 两大区）
     错误变体 '"area" <= 300' → 选 3 个小区（无警告框，纯视觉差异）
S2 Zoom to Selection          → 真值 extent_x0 ≈ −0.39（全范围为 2.00）
     错误变体 Zoom In（extent 大幅收缩）
S3 导出 GeoJSON（仅选中）      → 真值 文件恰好 {North, South}
     错误变体 全量导出 → 5 个要素
```

**结果**

| k（依赖链步数） | no-V | learned-V(S1) | **full-V(S1+S2+S3)** | truth-V |
|---|---|---|---|---|
| 1 | 0.333 | 0.583 | **0.917** | 1.000 |
| 2 | 0.083 | 0.333 | **0.667** | 0.917 |
| **3** | **0.083** | 0.250 | **0.917** | 0.833 |

- V(S1) **AUC=1.000**（校准 acc 1.000，信号 21.5/38.1）；V(S2) **AUC=1.000**；
  S3 直接读自己导出的文件（天然可验证，无需学习）。
- **full-V 增益相对 no-V：k=1 +0.583 → k=3 +0.833**，且把与 truth-V 的差距压到 ≈0
  （k=3 时 0.917 vs 上界 0.833，12 trials 内属同档）。
- no-V 随 k 崩塌（0.333 → 0.083 → 0.083）。

**已知局限（如实记录）**：V(S2) 的正确样本视觉信号很弱（diff=0.007），
它是靠"变化大 = 错"这一侧在工作；若正确缩放本身造成大幅画面变化，它会误判。
S3 走 PyQGIS（GUI 另存对话框是模态且动作名歧义），非 GUI 驱动。

# QGIS W11：验证不是免费的 —— 从"成功率"到"正确产物/分钟" ✅

> 复现：`python experiments/qgis/qgis_bridge/run_w11.py`　数据：`experiments/qgis/qgis_bridge/w11_results.json`

W10 证明了依赖链下 full-V 把成功率 0.083 → 0.917，**但那里验证是免费的**（重掷不花
任何东西）——这正是 §6 标为最高优先的遗留项。本轮给每个动作与每次验证记真实耗时，
在**固定时间预算**（150 s/模式）下连续跑任务，指标改为 **正确产物 / 分钟**。

**组件耗时（中位数，ms，QGIS 3.44 本机）**

| reset | S1 select_expr | S2 zoom | S3 export | **V 截图** | V 前向 | V 读文件 |
|---|---|---|---|---|---|---|
| 118 | 531 | 69 | 31 | **147** | **1.0** | **0.0** |

> **验证的成本几乎全部是"传感器"，不是模型**：截图占 99.3%，小 CNN 前向只有 1 ms。
> 而最便宜且充分的通道（读自己导出的文件）是 0 ms —— **选对通道比选对模型重要得多**。

**任务流（q=0.5，S1→S2→S3 依赖链，成功 = 产物 == {North, South} 且 extent 正确）**

| 模式 | 正确/总数 | 成功率 | **正确产物/分钟** |
|---|---|---|---|
| nov（不验证） | 16/189 | 0.085 | 6.38 |
| **full（三步都验证）** | 28/39 | **0.718** | **10.96（+72%）** |
| cheap（跳过 V(S2)） | 18/48 | 0.375 | 7.12 |
| full2x（验证直接成本 ×2） | 21/32 | 0.656 | 8.10（仍胜） |
| **full3x（×3）** | 13/24 | 0.542 | **5.10（已输给 nov）** |

**两条盈亏平衡（互相印证）**

1. **验证成本**：实测每次验证总开销 **522 ms**（2 次截图 + settle + 前向），
   由吞吐量等式反推可容忍上限 **992 ms → 余量 1.90×**。
   实证交叉：**×2 时 full 仍胜（8.10 > 6.38），×3 时已输（5.10 < 6.38）**——正好夹住 1.9×。
2. **策略质量**（更重要的那条）：V 只在对**弱策略**时才划算。
   no-V 吞吐 = 60·q^k/T₀，与 full 的 10.96/min 相交于 **q\* ≈ 0.53**（k=3）：

   | 每步成功率 q | 0.5 | 0.6 | 0.7 | 0.8 |
   |---|---|---|---|---|
   | no-V 产物/分钟 | 9.5 | 16.4 | 26.0 | 38.8 |
   | full 产物/分钟 | 11.0 | 11.0 | 11.0 | 11.0 |
   | 胜者 | full | **no-V** | no-V | no-V |

   → **"V 的价值"不是无条件成立的**：依赖式子目标让它从 0 变成正，
   但只有当**策略弱到 q < 0.53**（k=3）时它才在吞吐量上划算。
   q 高时验证是奢侈品：省下的失败不足以支付验证的时间。

**顺带修正的实验 bug（如实记录）**：`stream()` 的首版把 "before" 截图取在动作**之后**，
靠地图异步渲染的时序巧合才偶然得到了正确样本（成功率因此在 0.576–0.848 间乱跳）。
改正后成功率稳定在 0.718。**任何依赖"动作前后帧"的闭环实验都必须显式确认帧的先后**。

**局限**：时间成本是桥内特权调用的耗时（S1 的 531 ms 主要是表达式对话框的打开/关闭），
真鼠标下动作更贵（W4：810 ms vs 180 ms），会让 V 的相对成本更低、余量更大；
未测 GPU/远程桌面等更慢的截图路径。

# QGIS W12：把 actor 换成真模型 —— V 的价值塌缩（打自己脸的一轮）✅

> 复现：`python experiments/qgis/qgis_bridge/run_w12.py`　数据：`experiments/qgis/qgis_bridge/w12_results.json` / `w12_actor_data.npz`

W9–W11 的 actor 是"注入噪声的硬币"（每步 q=0.5，随机出错）。本轮训练**真 actor**：
在真 QGIS 上、从**真工具栏动作**里挑（指令是任务级短语，不是动作名），
每步候选 = 1 个正确 + 15 个从 live 池现抽的干扰项，**挑错就真执行、真出错**。

**三个步骤（全部真值可判）**

```
1) "把地图缩放到当前选中要素" → Zoom to Selection   （真值：extent_x0 = SEL 参照）
2) "把地图缩放到图层的完整范围" → Zoom Full          （真值：extent_x0 = FULL 参照）
3) "打开 Python 控制台"        → Python Console     （真值：console_visible）
```

**actor 的 q̂（288 样本 = 4 状态 × 3 步 × 24；候选 16 选 1；chance=0.06）**

| 通道 | in-domain | **未见 UI 状态** | 每步（未见状态） |
|---|---|---|---|
| **struct**（动作名 + bbox） | 1.000 | **1.000** | 1.00 / 1.00 / 1.00 |
| **pixel**（按钮裁剪 → CNN） | 0.861 | **0.826** | 1.00 / 1.00 / **0.48** |

**live 闭环（真 QGIS，150 s/格；V = 在 actor 错误分布上训练的截图验证器，AUC 1.000 / 0.814）**

| actor | 模式 | 每步成功率 | 整集全对 | **正确步/分钟** | 集数 |
|---|---|---|---|---|---|
| struct | no-V | **1.000** | **1.000** | **51.53** | 43 |
| struct | full-V | 0.967 | 0.900 | 45.88（**↓11%**） | 40 |
| pixel | no-V | 0.667 | 0.000 | 35.16 | 44 |
| pixel | full-V | 0.630 | 0.000 | **19.89（↓43%）** | 27 |

**三条结论**

1. **训练好的 struct actor 让 V 变成纯开销**：q̂=1.000 ≫ q\*=0.53（W11 的分水岭）——
   live 上 no-V 51.5 步/分、整集全对 1.000；加 V 反而掉到 45.9/0.900（截图成本 + 假阴性重掷）。
2. **V 修不了系统性错误**：pixel 的 Q3（"Python Console"按钮）**稳定认错**（0.48）——
   V 能判出失败（console 的真值验证近乎完美），但**重掷只会重复同一个错**，
   于是每步 0.667→0.630 没救回来，吞吐却腰斩（35.2→19.9）。整集 3 步全部失败。
3. **所以 W9–W11 的 V 增益是"硬币 actor"的产物**：硬币的错误是**均匀随机**的，
   重掷独立 → V 有效；真 actor 的错误是**系统性**的，重掷不独立 → V 无效。
   H2 的老结论再次出现：struct 1.000 vs pixel 0.826（且弱步 0.48）——换到端到端闭环仍然成立。

**过程中的四个真 bug / 设计修正（如实记录）**

1. 桥的 `win maximize` **在窗口被 resize 过之后就永远失效**（`showMaximized()` 静默无效）；
   `resize` 在最大化状态下也无效 → 修：先 `showNormal()`；maximize 亦然。这曾让"两种窗口尺寸"
   实为同一种，"未见状态"是假的。
2. 真值规则"更接近正确参照"**会被随机预置的 extent 骗**（随机子范围天然更接近全范围）
   → "Zoom Full" 标签 79% 假正例、V 学成 AUC 0.37 → 修：容差 + 最近参照双条件。
3. **任务在宽画布下病态**：选择框与图层框经 aspect 填充后视野几乎相同
   （margin 仅 0.14）→ 改选**单个小区域**（North），margin 拉到 3.4–4.4。
4. **控制台会改变画布尺寸** → 参照 extent 必须在该状态下标定，
   标定与每条 episode 都强制"控制台关闭"。

**设计选择的坦白**：候选池 = 24 个**不会弹模态框**的真工具栏动作（安全动作集），
这是环境设计决定（模态框会卡住 live 闭环）；未见状态 = 4 个（窗口尺寸 × 表达式对话框）中留出 2 个；
每格 150 s、n=27–44 集，有块噪声（±0.1 量级）。

> ⚠️ **W12 的 pixel 臂数字后来被证伪（见 W13）**：桥的**动作 rect 是错的**，
> 所以 pixel 臂是在错误裁剪上评测的；用真实 UIA rect 重测后 pixel 未见状态 = **1.000**。
> W12 的 struct 臂与"live 全对"结论不受影响（名字是对的，bbox 只是噪声特征）。

# QGIS W16：第一个真工作流 —— 纯 GUI 产出真 GeoJSON（含模态对话框）✅

前 15 轮都在缩放/控制台这类**无产物**动作上打转，且一直**绕开模态对话框**（W9 就是被它卡死的）。

```
右键图层 → Export（子菜单）→ Save [Selected] Features As…（模态对话框）
→ Format 选 GeoJSON → 填 File name → 勾/去勾 "Save only selected features" → OK → 磁盘出文件
```

**结果（7/7 全对）**

| 路径 | 成功 | 总耗时 | 菜单 | 对话框 | 落盘 |
|---|---|---|---|---|---|
| Save **Selected** Features As… → `sel.geojson` | **4/4** | **9.76 s** | 5.38 s | 3.29 s | 0.25 s |

**真实 GUI 路径慢 ~300×**，但它不需要任何进程内特权接口。这是"可达性 vs 速度"最锋利的一笔。

**四个实测发现（都可复用到别的应用）**

1. **子菜单在 UIA 里不存在**：一级上下文菜单是独立顶层窗口（UIA 可见其条目），
   但 Export 的**子菜单** UIA 完全看不到（像素截图里清清楚楚）→ 必须 `Right` 展开 + `Down`/`Enter` 选择。
2. **UIA 的菜单项列表会漏项**：这里漏了 "Toggle Editing"，导致按 UIA 索引数 Down 会**差一格**
   （实错了落在 "Make Permanent…"）→ 键步数必须按**渲染顺序**数，或改用别的锚点。
3. **对话框状态跨调用持久化**：`Save only selected features` 会被 QGIS 记住——
   不显式设定就会出现**静默错误产物**（"导出全部"实际只导了 2 个，因为上一轮勾过）。
   凡对话框字段都必须"读回校验"而不是"假定默认"。
4. **导出对话框的控件挂在主窗口的 UIA 树里**（不是独立顶层），automation_id 前缀
   `QgisApp.QgsVectorLayerSaveAsDialogBase`；OK 按钮是**系统本地化的**（界面英文、按钮"确定"）。

**局限（如实记录）**：选择（selection）仍由特权桥完成（环境设置），GUI 部分只覆盖"导出"这一段；
"Add saved file to map" 必须显式关掉，否则导出文件会回灌成新图层、污染后续上下文菜单。

# QGIS W18：零特权调用的完整工作流（Processing 选择 + GUI 导出）⚠️ 部分成立

> 复现：`python experiments/qgis/qgis_bridge/run_w18.py`　数据：`experiments/qgis/qgis_bridge/w18_results.json`

W16/W17 的导出是纯 GUI，但"选择"仍走特权桥。本轮把选择也搬上 GUI，
走 **Processing 工具箱**（QGIS 的标准自动化路径）：

```
Processing Toolbox（独立顶层窗口，UIA 可见）→ 搜索框 set_edit_text("Select by Expression")
→ 树筛出算法（Vector selection ▸ Select by expression）→ 双击
→ 算法对话框：Input layer 下拉 + Expression 行编辑（'"area" > 300'）+ Run
→ 图层选中 2 个 → 右键图层 → Export → Save Selected Features As… → 真 GeoJSON
```

**结果**

| 指标 | 数值 |
|---|---|
| 端到端全对 | **3/4**（裸首试 **3/4**；重试包装没救回失败那次——两次尝试都在 30 s 超时） |
| 成功时选择段 | **9.3 s**（工具箱置顶 ~0.4 s / 搜索 ~1.8 s / 对话框 ~1 s / Run+生效 ~5 s） |
| 成功时导出段 | 9.8 s（W16 路径） |
| **端到端**（成功时） | **~19.2 s**（对比：特权选择 + GUI 导出 = 9.8 s → 选择段贵 **~9.4 s**） |

**过程中修掉的同类陷阱**：`reset` 会重建图层，而**算法对话框的 Input layer 仍记着旧 layer id**
→ Run 校验失败、静默不选 → 修法与 W16 一致：**每轮显式重选输入图层**（不假定默认值）。

**未根因的失败模式（如实记录）**：偶发（~1/4）选择段完全无效果（Run 点了、30 s 内选择数不为 2），
且**重开一次对话框也救不回**，说明不是瞬时超时而是某种**持久化的坏状态**
（怀疑：残留的算法对话框被按标题误匹配、或工具箱搜索过滤把目标项藏起来）。
**"选择"段的自动驾驶可靠性目前只有 ~75%**，这是本轮最诚实的结论。

**顺带的正面结论**：Processing 工具箱是**独立顶层窗口且 UIA 完整可见**
（搜索框、算法树、参数表单、Run 按钮都有名字/rect/aid）——
比"菜单栏子菜单"（W17 遗留）好驱动得多，是复杂动作的**首选 GUI 路径**。

# QGIS W19：根因 W18 的偶发失败 —— 点击被"激活窗口"吃掉 ✅

> 复现：`python experiments/qgis/qgis_bridge/run_w19.py`（诊断） / `python experiments/qgis/qgis_bridge/run_w18.py`（修复后回归）

**诊断（6 次，3 失败）**：加仪表后发现失败时——

| 观测 | 失败时 | 成功时 |
|---|---|---|
| Input layer 组合框 | `regions [EPSG:4326]` ✓ | 同 |
| Expression 值 | `"area" > 300` ✓ | 同 |
| Run 按钮 enabled | True ✓ | 同 |
| **算法对话框的进度/错误标签** | **始终为空** | 同 |
| 选择计数 | 0（30 s 不恢复） | 0.5 s 内变 2 |

⇒ 参数全对、无报错、但动作没发生 → **Run 的点击根本没送达按钮**：
工具箱操作后焦点在工具箱，**对未聚焦对话框的第一下真鼠标点击被"激活窗口"吃掉了**
（偶发性来自焦点时序）。

**两种修法与代价**

| 修法 | 结果 | 选择段中位 |
|---|---|---|
| A. `set_focus()` + 验证后**再点一次** Run | 4/4 但常需重试 | 15.45 s（+6 s） |
| **B. 用 UIA `Invoke` 模式触发 Run**（不经过鼠标/焦点） | **4/4 且全首试** | **9.1 s** |

**修复后端到端**：零特权工作流（Processing 选择 + GUI 导出）**4/4 全对、~18.9 s**
（选择 9.1 s + 导出 9.7 s），产物真值 = 恰好 2 个要素。W18 的"~75% 可靠性"就此关闭。

**可复用结论**：对按钮类控件，**优先 UIA `Invoke` 而不是合成鼠标点击**——
不需要焦点、不受遮挡影响、不会出现"点了但没点到"的静默失败；
这与 W4 的"过期坐标点中隔壁按钮"、W16 的"对话框状态持久化"同属一族**静默错误**，
也是本项目反复出现的主题：**动作必须用结果验证，而不能假设发出即发生**。

## A. 感知通道

| # | 规则 | 证据 |
|---|---|---|
| A1 | **优先 UIA**：一次枚举拿到名字+rect，~20 ms；覆盖是硬约束（工具栏 17/28=61%，+菜单 26/28≈93%） | W13/W14 |

| A4 | **子菜单在 UIA 里不存在**（一级弹出菜单是独立顶层窗口），且菜单项列表会**漏项** → 嵌套菜单优先走**右键上下文菜单**路径，键步数按**渲染顺序**数 | W14/W16/W17 |

## B. 动作

| # | 规则 | 证据 |
|---|---|---|
| B1 | **按钮优先 UIA `Invoke`**：合成鼠标点击需要窗口聚焦，未聚焦窗口的**第一下点击会被"激活窗口"吃掉**（静默） | W19（W18 的 ~75%→4/4） |

| # | 规则 | 证据 |
|---|---|---|
| C1 | **UIA 句柄会过期** → 每次交互前**重新获取并校验**（否则 rect 失配、点到别处） | W17（W13 的"树瞬时为空"同源） |

| # | 规则 | 证据 |
|---|---|---|
| D1 | **复杂动作首选 Processing 工具箱**：独立顶层窗口、UIA 完整可见（搜索框/算法树/参数表单/Run），比菜单栏子菜单好驱动得多 | W18 |

# QGIS W21：自然语言 → 工作流参数（语言层），留出句式/取值 ✅

> 复现：`python experiments/qgis/qgis_bridge/run_w21.py [--e2e]`　数据：`w21_results.json` / `w21_model.pt`

W18/W19 的工作流参数是写死的（`"area" > 300`）。本轮补上语言层：
指令 → 表达式，用**未见句式**（新算子措辞）与**新取值**测泛化，并与"词法臂"对照。

**语料**：6 个训练句式 / 4 个未见句式（同语义槽位、不同句子结构、不同算子词），
2400 训练样本；学习臂 = 字符级 Transformer（4 层 d=128，~0.9M 参数，86 s 训练）；
词法臂 = 手写算子词表 + 数字/名字抽取（词表覆盖训练与测试用词）。

| 通道 | 已知句式 | 新取值 | **未见句式** |
|---|---|---|---|
| lexical（词表+抽取） | 1.000 | 1.000 | **1.000** |
| learned（0.9M 字符级） | 1.000 | **0/3** | **0.000** |

**失败模式**（与 W3 的动作名结论同构）：
· **未见算子词 → 退化为最频繁的模式**：`"至少300"` 被译成 `"a" > 3000`（既丢了字段名，也把 ≥ 当成 >）；
`"不是 West"` 被译成 `"name" = 'West'`（**否定直接丢失**）；
· **未见数字形状 → 不会"抄写"**：新数字 975/1025/1100 全错（训练里只有 100–950）。
即：**对已见措辞的新组合能泛化，对未见措辞/未见值形状不能**——这是数据分布学习，不是语义理解。

**端到端（真 QGIS，真值按指令语义手写）**：
- learned **2/4**：两条已知句式整链成功（选对→导出对），两条未见句式产出错文件（选错 → 导出错）；
- lexical **3/4**：唯一失败是一次工作流 hiccup（表达式正确、选择段未生效），非语言错误。

**本轮抓到的两个方法学坑（如实记录）**
1. **测例格式 ≠ 语料格式**：初版 E2E 的指令带空格（"大于 400"），而语料无空格 →
   学习臂 0/4 的"语义失败"其实是**格式 OOD**；改成与语料同格式后 2/4。
2. **真值不能从模型输出反推**：初版用"模型输出的表达式"算期望特征集，于是
   错表达式也会"通过"（lexical 曾显示 4/4 的假象）→ 改为**按指令语义手写真值**。

**结论**：语言层复现了 W3 的教训——**"词表 + 抽取"（结构）在三种切分上全胜，
代价是需要领域知识**；合理设计是"学习负责已见组合、词法兜底未见措辞"的混合。
并且语言层的错误会**直接污染产物**（选错→导出错文件），
只能靠"以指令语义核验产物"兜底——C3/C4 的又一处实例。

# QGIS W22：同一条端到端链上的三臂对照 —— "修低层" vs "加验证" vs "盲跑"，以及 V 的语言盲区 ✅

> 复现：`python experiments/qgis/qgis_bridge/run_w22.py`　数据：`experiments/qgis/qgis_bridge/w22_results.json`

W18→W19 的故事是：选择段的 Run 点击有 ~25% 概率被"激活窗口"吃掉（静默失败）。
本轮在同一条链（指令 → 表达式 → Processing 选择 → GUI 导出 → 文件真值）上对照三种处理：

| 臂 | 成功 | 总耗时中位 | 选择段中位 |
|---|---|---|---|
| **blind**（点一下就往下走，不验证） | **7/8** | 21.6 s | 11.7 s |
| **v-gated**（真鼠标点击 + 验证选择数 + 重试） | **8/8** | 19.7 s | 9.7 s |
| **invoke**（低层修复：UIA Invoke，不需焦点） | **8/8** | **19.5 s** | **9.6 s** |

**结论一：能修低层就别加验证。** 低层修复（invoke）零额外成本、100% 成功；
验证臂在这 8 次里没被触发（不受此样本的代价惩罚，W19 实测每次重试 +6 s）。
**验证是"修不了低层时"的通用退路，不是首选。**

**结论二（更硬）：步骤级 V 抓不到语言层错误——因为它是循环论证。**

| 指令 | learned 产出的表达式 | 步骤级 V（按该表达式算预期） | 指令级真值 | 文件 |
|---|---|---|---|---|
| "凡是面积至少300的区都导出来" | `"a" > 3000`（字段不存在） | **通过**（预期空集，实际空集） | **错** | [] |
| "名称不是West的区请导出" | `"name" = 'West'`（语义反了） | **通过**（预期 {West}，实际 {West}） | **错** | [West] |

**拦下 0/2**：V 用**同一个错参数**去算"预期"，所以永远自洽；
只有"以**指令语义**核验产物"才能发现，而那要求先**解决语言层**——
这解释了 W21 里端到端的失败为什么无法由 V 兜底。

**局限**：每臂 8 次（blind 的 1/8 失败率与 W18 的 1/4 有出入，样本小）；
语言盲区只测了两种错型（无效字段 / 否定丢失）。
**本轮之后，V 的完整画像**：需要依赖式子目标（W9/W10）、需要弱且随机的策略（W11/W12）、
需要可观测结果（W10）、且**对参数化错误无能为力**（W22）。

# QGIS W23：场景化任务集第一批（6 个矢量场景）执行基线 ✅

> 复现：`python experiments/qgis/qgis_bridge/run_w23.py --trials 3`　数据：`experiments/qgis/qgis_bridge/w23_results.json`　场景数据/真值：`data/scenario/` + `data/scenario_truth.json`　链构建块：`scn_gui.py`

W16–W19 验证的是单点链（选择、导出）。本轮把它们与新构建块（`scn_gui`：Processing 算法对话框 / 层属性的 GUI 驱动）合成为 **6 个具体 GIS 业务场景**，每场景 3 次独立试跑 —— 目标是立**执行基线**（机械可靠性 + 分段耗时）；指令文本（见 `w23_results.json` 的 `meta.instructions`）留给后续语言层采集。

| 场景 | 链 | 成功 | 总耗时中位 | 分段中位 |
|---|---|---|---|---|
| s1 专题渲染：roads 按 class 分类（4 类） | 层属性 → Categorized → Classify | 3/3 | 12.1 s | 12.0 |
| s2 选择导出：筛 primary 6 条 → 导出选中 | 表达式选择 → 导出 | 3/3 | 23.1 s | 12.8 / 10.4 |
| s3 缓冲：5 医院 × 150 km | Buffer → 导出 | 3/3 | 25.9 s | 16.1 / 9.8 |
| s4 组合：被服务区覆盖的 regions | Buffer → Extract by location → 导出 | 3/3 | 44.7 s | 16.1 / 18.9 / 9.7 |

导出段 9.7–10.4 s 与 W16（9.5 s）一致，可视为该链的稳定成本。

**本轮探明的三个新坑**（已沉进 `scn_gui.py` / `run_w16.py` 机械）：

1. **QMenu 高亮反馈是 `activeAction()`，不是 `currentAction()`** —— QMenu 上根本没有后者，
   Python 抛 AttributeError 被兜底吞掉 → 反馈恒为 None，键盘导航看着"永远找不对项"
   （截图证明 Down 实际在正常移动高亮）。修法后按 current 反馈步进；
   W16 的固定 Down 计数在 **item0 已被悬停高亮**时会越位（首 Down 落到下一项），
   而 QMenu 首项按 Up **不环绕**、Home **无效**。
2. **combo 选值失败时的 Esc 兜底会关掉整个对话框** —— 弹层已经关了，Esc 就落到对话框上
   （S1 实测：属性对话框被关 → 崩）。改法：只在桌面**真有** Qt 弹层 ListItem 时才按 Esc；
   前缀匹配放宽为 case-insensitive `startswith`（`categ` 要能命中 `Categorized`）。
3. **"Open output file after running algorithm" 必须保持勾选** —— 名字像"导出后打开文件"，
   实际控制**结果是否载入工程**；取消勾选 → 算法跑完却没有图层可导。

其它可复用机械：同名算法窗的**参数页/结果页并存**（只认带 Run 的，重试前先
Change Parameters 回退）；UIA 右键偶发不弹 → 3 次重试；临时输出层名 `Buffered_<uuid>`
与实际加载名可能不一致 → `resolve_layer` 前缀解析；算法等待 6 s 不够 → 20 s；
层属性的 Value/渲染器选择用 **combo type-ahead + 读回验证**（全桌面搜 ListItem 会串台到
别的应用，必须按 class 含 "Qt" 过滤）。

**局限**：每场景仅 3 试、单一米制数据集（EPSG:3857）、指令未过语言层
（W21 的表达式还不会从这 6 条中文指令生成）。
**下一步**：语言层接场景（指令 → 参数 → 链），把 18/18 的机械基线变成端到端训练/评测。

**本轮探明的四条硬经验**（都沉进 `map_gui.py`）：

1. **菜单加项统一走"单击 → New Item Properties 对话框"**：`Add Item → Add Map/Label/Legend`
   后单击页面，QGIS 弹出**内嵌子窗口** New Item Properties（X/Y/Width/Height +
   参考点 + 确定）——数值定位，不靠拖拽像素；而拖动放置反而不弹此框（map 的两种落法实测不同）。
2. **原生保存对话框会吃掉逐字键入的反斜杠**（中文 IME 环境）：`Export as Image…` 弹的是
   原生 `#32770` 保存对话框，`pyautogui.write("D:\\...")` 打进去变成
   `D:workcode...` → "文件名无效"警告；**必须剪贴板粘贴**（`win32clipboard` + Ctrl+V）。
3. **焦点陷阱升级版**：其它应用会抢前台，之后所有按键/点击静默打到别人身上 →
   操作对话框前先 `win32gui.SetForegroundWindow(hwnd)` 显式置前（本机实测被
   AI 客户端抢过两次）；另外鼠标停在屏幕角落会触发 pyautogui fail-safe。
4. **关闭/保存提示的中文按钮是"丢弃"**：布局未保存关闭 → 保存/丢弃/取消；
   残留提示会阻断后续所有 GUI 流程（实测挡住 Processing Toolbox → categorized 'open' 失败）
   → reset 里做防御性 `dismiss_prompts()`。

**局限**：单个复杂场景（未做多风格布局变体）；图例字体/标题字号用默认值（未走字体对话框）；
导出选项全用默认（300 dpi）；查询到的图层依赖 W24 真实数据链。
**下一步**：布局变体族（横/纵版、图例位置×标题字号×分级方式）作为"复杂示例"的第一批扩展。
