## 1. 清单构成（可复算）

解析 `artifacts/computer_use_inloop/audit_manifest.json`（n=216）：

| 项 | 数值 |
|---|---|
| 指令含引号标签（如 `'cities'`） | **188 / 216 = 87.0%** |
| 指令为泛化描述（`Click the combobox` / `Click the button`） | **28 / 216 = 13.0%** |
| 目标短边（全分辨率 2560×1440） | min 16px / **median 20px** / max 150px |
| 目标 <50px | **212 / 216 = 98.1%** |
| 目标 ≥100px | **4 / 216 = 1.9%** |

> 这两个数字决定了后面的一切：**43% 的目标只有 20px 宽**，而小模型的输入是 224px。

## 2. 已测 2B 两臂：复算（不是引用）

用 `audit_predictions/*.json` + 清单复算 top-1（点落在 `rect_img` 内）：

| 臂 | 总 top-1 | 含引号标签 | 泛化指令 | 延迟 p50 |
|---|---|---|---|---|
| UGround-V1-2B | **106/216 = 0.491** | 106/188 = **0.564** | **0/28 = 0.000** | **22.9 s** |
| GUI-Actor-2B | 94/216 = 0.435 | 94/188 = 0.500 | 0/28 = 0.000 | 1.95 s |

与 `AUDIT.md` 完全一致。**泛化指令 0/28 是能力边界，不是难度**：
指令里没有可见文字时，grounding 模型无从定位。

## 3. 220M 与清单的接口核对（本次最关键的发现）

| 项 | 小模型（仓库） | 216 清单 | 判定 |
|---|---|---|---|
| 输入分辨率 | `resize((224, 224))`（`audit_eval.py:236`，且 `do_resize=False`） | 1536×864（16:9） | 预处理可复用 |
| 坐标归一化 | 训练用 `x/1920, y/1080`（16:9） | 同上比例 | **兼容**（同为 16:9，归一化可直接换算） |
| **信息量** | 224px 宽 | 目标中位 **20px @2560** → 224 下约 **1.75px** | **不兼容** |

换算：`224 / 2560 ≈ 0.0875`；20px × 0.0875 ≈ **1.75px**。

这解释了一个旧数字：`self_grid128` 只有 **5.6%** —— 128 网格在 2560 宽屏上格宽约 20px，
目标本身就只有一个格子大，定位几乎不可能。

> 也就是说：**小模型在真实 GUI 上的低分，首先是"看不见"，不是"不会闭环"。**
> 在跑 82 分钟的 UGround 之前必须先解决这件事，否则比较的是分辨率而非闭环。

## 4. 功效（决定阶段 B 的最小规模）

| 设计 | 需要任务数 | n=216 是否够 |
|---|---|---|
| 配对（同任务两臂，McNemar，π_d=0.15） | 118 | ✅ |
| 配对（π_d=0.20） | 157 | ✅ |
| 配对（π_d=0.30） | 235 | ❌（差 19） |
| 非配对（两比例，p≈0.5） | 377–392 / 臂 | ❌ |

补充：n=216、p=0.5 时 Wilson 半宽 **±6.7pp**；n=400 时 ±4.9pp。

→ **216 条只在"配对比较"下够用**；若要把两臂当独立样本比较，必须扩到 ≈400/臂。
这一条要在正式预注册里写死，避免"看起来差不多"就当结论。

## 5. 合成域：能进区间，但任务族不对

| 证据 | 数值 | 含义 |
|---|---|---|
| P0 `cls`（fill 0.40/0.75，w32） | **1.000** | 默认难度 = 天花板 |
| H4 C0（无干扰）w4→w32 | 0.938 → 0.999 | 天花板 |
| H4 C1（1 干扰/格）w16 | 0.877 | **区间内** |
| H4 C2 w12 | 0.701 | 区间内 |
| H4 C3（4 干扰/格）w32 | 0.602 | 区间内 |

所以**"合成域必然天花板"这个说法要修正**：加干扰项后，220M 完全可以落在 `[0.25, 0.85]`。

但另一条限制更硬：**合成元素 4–8px，没有文字**（`H4_GENERALIZATION_PREREG.md` §7.1 实测：
`render()` 只在宽度 ≥30 时画字）。也就是说合成任务是**颜色匹配**，不是文字接地。
而两个 2B 臂在**无文字**任务上的实测类比是 **0/28 = 0%**。

→ 合成域对 2B 臂是**能力不匹配**（不是难度不足）。要么给元素加文字（改变任务族，
且会重新引入 M3 的颜色捷径问题），要么承认合成域只能作**对照臂**。

## 6. A2 判定与两条杠杆

**判定：FAIL（现有资产）**。原因（按可修性排序）：

| # | 阻塞 | 影响的臂 | 杠杆 |
|---|---|---|---|
| 1 | 输入 224²，目标中位 20px → 1.75px | 220M | **提高观察分辨率**（1024 输入 / 分块裁剪），并把额外计算计入成本 |
| 2 | 无文字任务上 grounding 臂 = 0 | UGround / 8B | **换任务族**（给元素加文字）或换测试域 |
| 3 | 泛化指令 0/28 | 两个 2B | 主比较集限定为"含可见标签"的 188 条，28 条单列 |

三者都是**设计变更**，不是"调难度"。按 A2 纪律：**不降门槛、不删难例、不换种子**。

## 7. 阶段 B 之前必须先做的三件事（仍不推理）

1. 定 **220M 的观察分辨率方案**（224 / 512 / 1024 / 分块），并给出每档的 FLOPs 与显存估算；
2. 定 **主比较集**：188 条（含标签）作主集，28 条泛化指令作能力边界单列；
3. 定 **配对设计**并确认 216 条够不够（按 π_d 选 188 还是需补到 235+）。

这三件做完，阶段 B（UGround 82 分钟 + 220M 几分钟 + 8.8B 未验证）才有意义。
