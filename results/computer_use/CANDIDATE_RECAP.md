## 1. 结论

> **候选召回问题解决了，排序成为新瓶颈。**
> 同帧对照：旧口径 30.4% → 新口径 **91.9%**（目标 ≥80%，达标）。
> 但代价是候选数从 58 涨到 **332/帧**，排序 top-1 反而从 40% 掉到 **22.1%**。
> 端到端 0.919 × 0.221 = **20.3%**，仍远低于纯视觉 A3u 的 **62.5%**。

## 2. B1：召回（同帧对照）

| 候选口径 | 召回 | 候选中位 |
|---|---|---|
| 旧：60 条截断，仅控件 | **30.4%**（49/161） | 58 |
| 新：actions + widgets，无上限 | 76.4%（123/161） | 208 |
| 新 + **UIA 合并** | **91.9%**（68/74） | **332** |

三轮的口径变化：
1. **QAction 列表**提供了图标按钮的语义（50 条/帧，带 text+rect）；
2. 去掉 60 硬截断；
3. **UIA 补充**菜单栏项、树项、标题栏按钮（约 117 条/帧）——bridge 拿不到的那部分。

> 口径警告：不做容器过滤时召回是 89.8%，那是 `QgisApp` 全窗口矩形造成的假象；
> 本报告所有召回都已排除容器（面积 >25% 屏幕或容器类名）。

说明卡在启动/更新检查），因此先用**健康运行时的一次 UIA 导出**（`bigemap_controls.txt`）
整理为标准样本 `artifacts/uia_capture/bigemap/tree_legacy.json`：

| 指标 | 值 |
|---|---|
| 控件总数 | 97 |
| 有名字 | 97（100%） |
| 名称+可操作（Button/Menu/Tab/Combo/TreeItem…） | **59** |
| 类型分布 | Text 26 / Button 17 / TreeItem 9 / MenuItem 8 / RadioButton 8 / ComboBox 6 / TabItem 6 |

两条结论：

1. **标准 Qt 控件 UIA 覆盖良好**：菜单、工具栏、下拉、树项都在，且都带名字和矩形。
2. **这份早期导出里看不到级别表**：97 个控件里没有下载对话框的"级别"表格。
   后来单独抓下载对话框时才发现，它其实**在 UIA 树里读得到**（36 个 `DataItem`），
   只是**没有任何可操作 pattern**——"缺失"更准确的说法是"可读不可操作"，见 §8.3。

### 8.1 主窗口实时抓取（应用重新打开后）

`artifacts/uia_capture/bigemap/tree_main.json`（248 个节点）：

| 指标 | 值 |
|---|---|
| 节点总数 | **248** |
| 有名字 | 97（39%） |
| 名称+可操作 | **59** |
| **Custom（自绘）节点** | **72，全部无名** |
| 其余 | Button 45 / Text 26 / Radio 19 / CheckBox 17 / TreeItem 9 / MenuItem 8 / ComboBox 6 |

这条数据把分工量化了：**自绘控件在 UIA 里"存在但不可命名"**（72 个 Custom 节点），
所以候选生成不能只按名字过滤——要么给 Custom 节点补几何聚类，要么交给视觉。

### 8.2 对话框打开时的对比

同一应用、打开「导入边界」与「选择文件」两个对话框后重抓：

| 状态 | 节点 | 有名 | 可操作 |
|---|---|---|---|
| 仅主窗口 | 248 | 97 | 59 |
| **主窗口 + 两个对话框** | **485** | **317** | **258** |

多出来的节点几乎全在对话框里：`Edit 83`、`ListItem 86`。
**这直接说明候选生成的覆盖率高度依赖"当前处于哪个界面状态"**——
只抓主窗口，会把导入/下载流程里真正要点的控件全部漏掉。

### 8.3 下载对话框：自绘级别表是"可读不可操作"

`artifacts/uia_capture/bigemap/tree_download.json`（`下载对话框`，103 节点 / 91 有名）：

| 类型 | 数量 |
|---|---|
| **DataItem（级别表单元格）** | **36** |
| ListItem / Text / Button | 13 / 7 / 6 |
| RadioButton / CheckBox / Header | 5 / 4 / 5 |
| Custom / Edit / ComboBox | 7 / 2 / 2 |
| Table | 1 |

级别表结构完整可读：`Table` 1 个（478×265），4 列表头（级别/比例尺/尺寸/理论大小），
9 行 × 4 列 = 36 个 `DataItem`，名字是 `第0级`…`第8级`、`1:271416282`、`0x0`、`0.00 K`。
**这次不用视觉 OCR，UIA 就能把整张表读出来。**

但"能读"不等于"能操作"：

```
row.is_selected()      -> NoPatternInterfaceError
row.get_toggle_state() -> AttributeError
```

9 个级别行**没有任何 Selection / Toggle / Invoke pattern**，表格里也没有复选框字形
（截图核对过：`第N级` 文字紧贴单元格左边，无勾选框）。也就是说：

- 选中态无法通过 UIA 读取，也无法通过 UIA 设置；
- 只能用几何点击去"猜"行选中，且点了是否生效没有原子断言可验。
- 这正好解释了之前"手动点击复选框无效"——**根本没有复选框**，交互是行选中。

### 8.4 窗口化 vs 最大化：不影响可读性，影响的是别的东西

主窗口从最大化（2568×1400）改成窗口化（1600×1000）后：对话框仍有 **94 节点**
（最大化时 103，差的是被窗口下边界裁掉的表格行），表格文字全部照常读出。
**窗口化完全可操作，不需要最大化。**

真正卡住自动化的三件事（与窗口模式无关，都已修复）：

| 现象 | 根因 | 处理 |
|---|---|---|
| `descendants()` 返回 0 | `element_info.auto_id` 在 Qt 节点上抛 `AttributeError`，被逐节点 `except` 吞掉 | 单属性兜底 `_auto_id()` |
| 整窗查不到 | 被 Chrome 全屏遮挡时 UIA 判 offscreen，`visible_only=True` 过滤掉整窗 | 改 `win32gui` 枚举句柄 + `Desktop.window(handle=)` |
| 句柄 rect 是 -32000 | 该窗口**失焦会自己最小化** | 操作前 `ShowWindow(SW_RESTORE/MAXIMIZE)` |

这三条是"UIA 在真实桌面应用上跑"的通用坑，写进采集器默认路径，不再逐次踩。

### 8.5 可操作性分三层：读得到 / 点得动 / 验得了

同一个应用里，控件按能力分成三档，这比"UIA 覆盖率高不高"更有用：

| 层级 | 例子 | 能力 |
|---|---|---|
| 标准控件 | Button / MenuItem / Edit / TreeItem（主窗 258 个可操作里有名的一批） | 有名字、有 rect、支持 invoke → **可读可点可验** |
| 自绘表格行 | 级别表的 36 个 `DataItem`（`第0级`…`第8级`） | 有名字、有 rect，但无 Selection/Toggle pattern → **可读不可设、不可验** |
| 自绘画布 | 地图区域、Rectangle 面板（`Custom`） | 无名字，只能几何定位；合成拖拽不被接受 |

画布那条有直接证据：工具条「矩形框」用 UIA `select()` 选中成功（按钮高亮可见），
随后在地图上合成拖拽 300×220，**结果被解释成地图平移**（视图从中国移到北欧），
没有生成 `Rectangle #2`，复现两次。也就是说自绘画布只认真实鼠标输入，
合成拖拽不成立——这和之前"下载对话框里点复选框无效"是同一类问题。

窗口摆放：`place_bigemap_topright.py` 把窗口固定到 `(1344,16)-(2544,916)`（1200×900，右上角），
窗口化后 UIA 可读性不变，且不再遮挡桌面。

### 8.6 精确 AOI：走导入，不画框

**结论：这个画布不接受合成鼠标输入，所以"点两下画矩形"对自动化不可用；
正确路径是导入边界（SHP），AOI 精确到坐标。**

画布的证据是两条：

| 动作 | 结果 |
|---|---|
| `矩形框` 用 UIA `select()` 选中（`is_selected()=1`），再在地图上**点击两次** | 不生成矩形，状态栏读数证明点击落点正确（SW `116.215825,39.906247`、NE `116.226146,39.913209`） |
| 同一状态在地图上**拖动** 481×423 px | 被解释为**地图平移**（视图从石景山移到别处） |

也就是说：坐标是准的，画布只是不认合成事件。靠拖拽去"试"是纯浪费。

导入链路（全部可验证）：

1. `定位` 对话框里要填**「有偏移」那一组**（GCJ-02），
   无偏移那组只是输入源：填 WGS84 → 点`加偏` → 有偏移自动算出
   `116.220100,39.911800 → 116.2261600972,39.9130317035`（北京偏移量吻合）。
   只填无偏移直接点`定位`是**没反应**的，这是之前"定位无效"的原因。
2. 缩放到 `级别 16`（AOI 约 1.1 km，1.83 m/px → 480×422 px）。
3. `导入边界` → `...` → 选 SHP → `选择区域` 里**勾选复选框**（不是点行）→ `确定`。
4. 导入后地图上的矩形面板读数：`116.2101,39.912 >> 116.220,39.905`、`面积 0.685 平方公里`；
   GDAL 算的 AOI 是 879 m × 774 m = **0.680 km²**，一致（面板四舍五入到 4 位小数）。
5. 双击矩形内部 → 下载对话框（103 节点，与 §8.3 结构一致）。

### 8.7 四个把自动化卡死的工程坑

这四个都不是"识别"问题，而是"没验证前提就往下走"：

| 坑 | 现象 | 根因 | 正确做法 |
|---|---|---|---|
| **反斜杠被吞** | 反复报"文件名无效" | `pyautogui.write(r"C:\Users\...")` 在这台机器上打出 `C:Usersgf191…` | 用剪贴板 `Ctrl+V` 粘贴路径 |
| **按钮找不到** | 点了没反应/点错 | `打开(O)` 是 **SplitButton**，只查 `Button` 就漏 | 同时匹配 `Button` 和 `SplitButton` |
| **文件被判无效** | `sjs_aoi.kml 文件无效` | KML 本身合法（GDAL/LIBKML 读出 1 要素、范围正确），是 Bigemap 的 KML 解析器挑食 | 用 GDAL 转 **SHP**（它的原生态格式）并本地复验 |
| **区域选不中** | 提示"请选择一个要导入的区域" | 树里是**复选框**，行选中不算数；且提示框是模态的，挡住后续点击 | 点复选框本身；提示框用 `Enter` 关（`click_input` 无效） |

教训写在前面那句：**每个外部输入（文件合法性、控件类型、选中语义）都先验证，再点下一步。**
