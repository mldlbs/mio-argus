# 真实站点上的结构通道（`real_site_agent.py`）

> 复现：`python experiments/web/real_site_agent.py`（6 个真实站点，系统 Chrome，headless）
> 数据：`results/web/real_site_agent_results.json`

---

## 1. 设置

- 观测：注入 JS **element table 提取器**，两个版本：
  - **v1**：15 行，只扫 `document`，名字取 aria-label/placeholder/innerText。
  - **v2**：递归 **shadow root / 同源 iframe**（深度 3），补全命名
    （aria-label / aria-labelledby / placeholder / title / img alt / `<label>` / name / value），
    过滤 `aria-hidden` 与不可见。
- 目标：`search / login / home / logo` 四类。
- 对照：规则 oracle（role/属性/`is_logo`）vs **关键词策略**（只用元素名字）。
- 指标：`found`（在表里）、`hit`（策略选中）、快照耗时、表规模。

---

## 2. 结果：v1 vs v2

| 任务 | v1 found | v1 hit | v2 found | **v2 hit** |
|---|---|---|---|---|
| search | 0.500 | 0.500 | 0.667 | **0.500** |
| login | 0.500 | 0.500 | 0.500 | **0.500** |
| home | 0.167 | 0.167 | 0.333 | **0.167** |
| logo | 0.500 | 0.167 | 0.667 | **0.333** |

| | v1 | v2 |
|---|---|---|
| 表规模（median） | 26 | **213** |
| 快照耗时（median） | 6.4 ms | **19.6 ms** |

站点级：mdn 6→77、github 7→112、wikipedia 60→**1412**。

---

## 3. 两条（修订后的）结论

1. **可用性是提取器问题，不是站点问题**（v1 → v2 把 found 抬了约 1.3–2×；
   表规模翻 8 倍）。所以"真站缺结构"这个说法基本不成立——
   **结构在那里，但你要付一笔提取器工程费**（递归 shadow/iframe、命名补全、可见性）。
   这正是 [jev-ultrafast](https://github.com/browser-use/jev-ultrafast) 把 `snapshot.js` 当核心工程的原因。

2. **但"选择是免费的"只在小表上成立**（上一轮 v1 的 19/19）。
   表一旦变真实（213 个元素、命名噪声），关键词策略**精度掉下来**：
   `search 0.667→0.500`、`home 0.333→0.167`、`logo 0.667→0.333`。
   → 瓶颈从"找元素"**转移到了"命名与排序"**——这需要
   **在 element table 上学一个策略**（jev 的 op/target heads；本项目的 W11 索引化动作空间）。

> 合起来：**structure recovery = 提取器（可用性）× 命名（可选择性）**。
> WinSim 里这两项都被 DOM 白送（1.000）；真站里它们各要一份工程。

---

## 3.5 学习型策略 vs 关键词（`real_site_policy.py`）—— 一个负面结果

上一节说"瓶颈转移到命名/排序，需要在表上学策略"。照着做了：12 个站点、v2 提取器，
训练样本 = 每个有名元素（指令就是它的名字），
模型 = char-trigram 多热 + role/bbox 的共享文本编码打分；
**站点级 held-out**（训练 7 站 → 测试 5 个从未见过的站）。

| | 结果 |
|---|---|
| 名字匹配（训练站） | 0.716 |
| **名字匹配（held-out 站点）** | **0.184** |
| 规范任务（零样本，held-out 站点）learned | **0.000**（n=1/2/1/4） |
| 规范任务 keyword 基线 | **0.750**（search/login/home 1.000，logo 0.500） |

**读法**：
1. **站点级泛化很差**（0.716 → 0.184）：模型记住了训练站点的名字，换个站就掉到 0.18。
   这与 `W5/W11` 的结论同向——**未见应用/站点对学习型策略是硬伤**。
2. **零样本任务概念迁移失败**：让它找"search"（指令不是任何元素的名字），在未见站点上 0.000，
   而**关键词基线 0.750**。
3. **与 P8 同源**：小数据下，**人工先验 > 小学习模型**（P8：干净背景上经典 CV 0.847 vs
   学习检测器 0.518）。这里的先验就是"任务词关键词"。

**限定（必须说清）**：训练样本只有 356（受 64 候选上限与站点数限制）、模型很小、60 epoch；
规范任务的正样本只有 1–4 个，噪声大。所以这是"**在这个规模下**学习型策略不划算"，
**不是**"学习型策略不可能赢"。要翻案需要：更多站点、更大候选上限、更强的文本编码。

### 3.6 扩数据重测（站点 24→8 held-out，候选 64→300，编码加非线性）

把三个限制都放开后（**训练 2600 样本 / held-out 951 / 模型 207K 参数**）：

| | 小数据版（v1） | **扩数据版（v2）** |
|---|---|---|
| 名字匹配 · 训练站 | 0.716 | **0.836** |
| 名字匹配 · **held-out 站点** | 0.184 | **0.386** |
| 规范任务 learned vs keyword | 0.000 vs 0.750 | **0.312 vs 0.375** |
| — 分任务 | — | search .25/.50、login **.67/.33**、home .33/.67、logo .17/.17 |

**修订后的结论（仍未翻案）**：

1. **数据规模确实有效**：held-out 名字匹配 0.184 → **0.386**（2.1×）。
2. **但站点级过拟合依旧**：训练 0.836 vs held-out 0.386——差距没缩小，只是两边一起抬高。
3. **规范任务上接近持平**（0.312 vs 0.375），并在 **login 上反超**（0.67 vs 0.33）；
   但每个任务只有 **n=3–6** 个正样本，噪声大，**不足以宣布翻案**。

> 迄今最诚实的表述：**在"几十个站点 / 几千样本"这个规模上，学习型策略与人工关键词先验大致打平，
> 但站点级泛化仍明显不足**。这与 P8（小数据下先验更强）不矛盾，只是把"更强"改成了"差不多"。

要真正判定，需要**成百站点 / 更大候选上限 / 更强的文本或视觉编码**——
这是目前这条线上唯一还没做完的实验。

## 3.7 提取器 v3（跨 frame 闭合）与可点性漏斗（`real_site_reach.py`）

> 复现：`python experiments/web/real_site_reach.py --quick` / 去掉 `--quick` 为全量
> 数据：`results/web/real_site_reach_results.json`

v2 的快照是页面内 JS：同源 iframe 靠 `contentDocument`（跨域为 null），而且
"found" 只说明**结构里有**，不说明**点得到**。本轮补两块（全量：7 个真实站 +
1 个受控 harness，8 站 × 4 任务）：

**1. v3 = 逐 Playwright frame 注入（跨域闭合）**

| | v2（页内 JS） | v3（frame tree） |
|---|---|---|
| 真实 7 站元素数 | 与 v3 相同 | **+0**（organic 跨域条目 = 0） |
| 受控 harness（OSM 跨域 iframe） | **0** | **7**（跨域 frame 内 7 个可交互元素） |
| 快照耗时（median） | 11.4 ms | 11.9 ms（**+0.5 ms**） |

两个结论：
- **v3 的闭合能力是真的**（harness 里 v2 全盲、v3 全进）；
- **但这 7 个真实站上跨域闭合收益 = 0**——四类任务目标与常见站的可交互元素
  根本不落在跨域 frame 里。跨域是能力储备，不是当前任务的瓶颈。

**2. found → reachable 漏斗**（对关键词策略选中目标：滚动进视口 →
elementFromPoint 命中 → 真实点击）

| 级 | 比率 | 说明 |
|---|---|---|
| found（真实 6 站 oracle） | 12/24 = 0.500 | 对齐 §2 口径，v2 = v3 |
| pick（关键词选中） | 19/32 = 0.594 | 含 harness/yt 的 0 |
| hit \| pick | 17/19 = **0.895** | 滚动后 elementFromPoint 命中 |
| click_ok \| 尝试 | 16/19 = **0.842** | Playwright actionability 通过 |
| 表级可达率（视口内抽样 232 个） | 220/232 = **0.948** | 未被遮挡的比例 |

**读法**：结构通道的"found"在真实站上**基本等于"点得到"**——
静态遮挡只吃掉约 5%（mdn 的 sticky 区域最差 7/14）。三类真实损失各归其位：

1. **状态折叠（offscreen）**：mdn 的 search/login 在 1000×700 视口下
   折叠在头部之外，滚动也不出现（元素存在但需要先交互才展开）——
   found 但不可达，2 个 click_timeout 全在这；
2. **静态命中 ≠ 动态可点**：wikipedia login 的 hit=True 但
   Playwright 点击超时（滚动后 sticky 元素移位/稳定性检查失败）——
   漏斗两级都要测，不能用命中代替点击；
3. **no_pick**：hn/logo、mdn/home 等关键词选不中（命名层问题，§2/§3.5 已测）。

与 WinSim 对照：像素端到端 0.79 里包含检测+接地+点击的全部损失；
真站结构通道把这条链缩到 **pick → click 两级，且两级都在 0.85+**
（表级 0.95）。**"结构在那里"这句在 7 个真实站上成立，代价仍是
提取器工程费（v2/v3 的 213 行 JS）而不是可用性。**

**局限**：弹窗遮挡未构成样本（8 站加载时全屏 overlay = 0，headless/地区
无 cookie 横幅）；点击成功 ≠ 任务成功（本实验只量"点得到"，未验后续状态）；
跨域能力只在受控 harness 验证，真实站 organic 样本为 0。

## 4. 与总报告的关系

| | WinSim（受控） | 真站 v1 | 真站 v2 |
|---|---|---|---|
| 结构可用性 | 1.000 | 0.17–0.50 | **0.33–0.67** |
| 给定表的选择 | 0.93–1.00（学习型） | 1.00（表小） | **0.17–0.50（关键词失效）** |
| 快照成本 | — | 6.4 ms | 19.6 ms |
| 像素端到端 | 0.79 | 未测 | 未测 |

与 `REPORT §8.5` 一致且更细：**成本中心是"把结构恢复出来"，而恢复 = 提取 + 命名**。
像素通道在结构不可得时付 0.6（WinSim canvas 区）；结构通道在真站上付的是**提取器与命名的工程费**。
