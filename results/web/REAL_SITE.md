# 真实站点上的结构通道（`real_site_agent.py`）

> 复现：`python experiments/web/real_site_agent.py`（6 个真实站点，系统 Chrome，headless）
> 数据：`results/web/real_site_agent_results.json`

---

## 1. 设置

- 观测：注入 JS **element table 提取器**，两个版本：
  - **v1**：15 行，只扫 `document`，名字取 aria-label/placeholder/innerText。
  - **v2**：递归 **shadow root / 同源 iframe**（深度 3），补全命名
    （aria-label / aria-labelledby / placeholder / title / img alt / `<label>` / name / value），
    过滤 `aria-hidden` 与不可见。
- 目标：`search / login / home / logo` 四类。
- 对照：规则 oracle（role/属性/`is_logo`）vs **关键词策略**（只用元素名字）。
- 指标：`found`（在表里）、`hit`（策略选中）、快照耗时、表规模。

---

## 2. 结果：v1 vs v2

| 任务 | v1 found | v1 hit | v2 found | **v2 hit** |
|---|---|---|---|---|
| search | 0.500 | 0.500 | 0.667 | **0.500** |
| login | 0.500 | 0.500 | 0.500 | **0.500** |
| home | 0.167 | 0.167 | 0.333 | **0.167** |
| logo | 0.500 | 0.167 | 0.667 | **0.333** |

| | v1 | v2 |
|---|---|---|
| 表规模（median） | 26 | **213** |
| 快照耗时（median） | 6.4 ms | **19.6 ms** |

站点级：mdn 6→77、github 7→112、wikipedia 60→**1412**。

---

## 3. 两条（修订后的）结论

1. **可用性是提取器问题，不是站点问题**（v1 → v2 把 found 抬了约 1.3–2×；
   表规模翻 8 倍）。所以"真站缺结构"这个说法基本不成立——
   **结构在那里，但你要付一笔提取器工程费**（递归 shadow/iframe、命名补全、可见性）。
   这正是 [jev-ultrafast](https://github.com/browser-use/jev-ultrafast) 把 `snapshot.js` 当核心工程的原因。

2. **但"选择是免费的"只在小表上成立**（上一轮 v1 的 19/19）。
   表一旦变真实（213 个元素、命名噪声），关键词策略**精度掉下来**：
   `search 0.667→0.500`、`home 0.333→0.167`、`logo 0.667→0.333`。
   → 瓶颈从"找元素"**转移到了"命名与排序"**——这需要
   **在 element table 上学一个策略**（jev 的 op/target heads；本项目的 W11 索引化动作空间）。

> 合起来：**structure recovery = 提取器（可用性）× 命名（可选择性）**。
> WinSim 里这两项都被 DOM 白送（1.000）；真站里它们各要一份工程。

---

## 3.5 学习型策略 vs 关键词（`real_site_policy.py`）—— 一个负面结果

上一节说"瓶颈转移到命名/排序，需要在表上学策略"。照着做了：12 个站点、v2 提取器，
训练样本 = 每个有名元素（指令就是它的名字），
模型 = char-trigram 多热 + role/bbox 的共享文本编码打分；
**站点级 held-out**（训练 7 站 → 测试 5 个从未见过的站）。

| | 结果 |
|---|---|
| 名字匹配（训练站） | 0.716 |
| **名字匹配（held-out 站点）** | **0.184** |
| 规范任务（零样本，held-out 站点）learned | **0.000**（n=1/2/1/4） |
| 规范任务 keyword 基线 | **0.750**（search/login/home 1.000，logo 0.500） |

**读法**：
1. **站点级泛化很差**（0.716 → 0.184）：模型记住了训练站点的名字，换个站就掉到 0.18。
   这与 `W5/W11` 的结论同向——**未见应用/站点对学习型策略是硬伤**。
2. **零样本任务概念迁移失败**：让它找"search"（指令不是任何元素的名字），在未见站点上 0.000，
   而**关键词基线 0.750**。
3. **与 P8 同源**：小数据下，**人工先验 > 小学习模型**（P8：干净背景上经典 CV 0.847 vs
   学习检测器 0.518）。这里的先验就是"任务词关键词"。

**限定（必须说清）**：训练样本只有 356（受 64 候选上限与站点数限制）、模型很小、60 epoch；
规范任务的正样本只有 1–4 个，噪声大。所以这是"**在这个规模下**学习型策略不划算"，
**不是**"学习型策略不可能赢"。要翻案需要：更多站点、更大候选上限、更强的文本编码。

### 3.6 扩数据重测（站点 24→8 held-out，候选 64→300，编码加非线性）

把三个限制都放开后（**训练 2600 样本 / held-out 951 / 模型 207K 参数**）：

| | 小数据版（v1） | **扩数据版（v2）** |
|---|---|---|
| 名字匹配 · 训练站 | 0.716 | **0.836** |
| 名字匹配 · **held-out 站点** | 0.184 | **0.386** |
| 规范任务 learned vs keyword | 0.000 vs 0.750 | **0.312 vs 0.375** |
| — 分任务 | — | search .25/.50、login **.67/.33**、home .33/.67、logo .17/.17 |

**修订后的结论（仍未翻案）**：

1. **数据规模确实有效**：held-out 名字匹配 0.184 → **0.386**（2.1×）。
2. **但站点级过拟合依旧**：训练 0.836 vs held-out 0.386——差距没缩小，只是两边一起抬高。
3. **规范任务上接近持平**（0.312 vs 0.375），并在 **login 上反超**（0.67 vs 0.33）；
   但每个任务只有 **n=3–6** 个正样本，噪声大，**不足以宣布翻案**。

> 迄今最诚实的表述：**在"几十个站点 / 几千样本"这个规模上，学习型策略与人工关键词先验大致打平，
> 但站点级泛化仍明显不足**。这与 P8（小数据下先验更强）不矛盾，只是把"更强"改成了"差不多"。

要真正判定，需要**成百站点 / 更大候选上限 / 更强的文本或视觉编码**——
这是目前这条线上唯一还没做完的实验。

## 3.7 提取器 v3（跨 frame 闭合）与可点性漏斗（`real_site_reach.py`）

> 复现：`python experiments/web/real_site_reach.py --quick` / 去掉 `--quick` 为全量
> 数据：`results/web/real_site_reach_results.json`

v2 的快照是页面内 JS：同源 iframe 靠 `contentDocument`（跨域为 null），而且
"found" 只说明**结构里有**，不说明**点得到**。本轮补两块（全量：7 个真实站 +
1 个受控 harness，8 站 × 4 任务）：

**1. v3 = 逐 Playwright frame 注入（跨域闭合）**

| | v2（页内 JS） | v3（frame tree） |
|---|---|---|
| 真实 7 站元素数 | 与 v3 相同 | **+0**（organic 跨域条目 = 0） |
| 受控 harness（OSM 跨域 iframe） | **0** | **7**（跨域 frame 内 7 个可交互元素） |
| 快照耗时（median） | 11.4 ms | 11.9 ms（**+0.5 ms**） |

两个结论：
- **v3 的闭合能力是真的**（harness 里 v2 全盲、v3 全进）；
- **但这 7 个真实站上跨域闭合收益 = 0**——四类任务目标与常见站的可交互元素
  根本不落在跨域 frame 里。跨域是能力储备，不是当前任务的瓶颈。

**2. found → reachable 漏斗**（对关键词策略选中目标：滚动进视口 →
elementFromPoint 命中 → 真实点击）

| 级 | 比率 | 说明 |
|---|---|---|
| found（真实 6 站 oracle） | 12/24 = 0.500 | 对齐 §2 口径，v2 = v3 |
| pick（关键词选中） | 19/32 = 0.594 | 含 harness/yt 的 0 |
| hit \| pick | 17/19 = **0.895** | 滚动后 elementFromPoint 命中 |
| click_ok \| 尝试 | 16/19 = **0.842** | Playwright actionability 通过 |
| 表级可达率（视口内抽样 232 个） | 220/232 = **0.948** | 未被遮挡的比例 |

**读法**：结构通道的"found"在真实站上**基本等于"点得到"**——
静态遮挡只吃掉约 5%（mdn 的 sticky 区域最差 7/14）。三类真实损失各归其位：

1. **状态折叠（offscreen）**：mdn 的 search/login 在 1000×700 视口下
   折叠在头部之外，滚动也不出现（元素存在但需要先交互才展开）——
   found 但不可达，2 个 click_timeout 全在这；
2. **静态命中 ≠ 动态可点**：wikipedia login 的 hit=True 但
   Playwright 点击超时（滚动后 sticky 元素移位/稳定性检查失败）——
   漏斗两级都要测，不能用命中代替点击；
3. **no_pick**：hn/logo、mdn/home 等关键词选不中（命名层问题，§2/§3.5 已测）。

> ⚠️ **第 1 条已被 §7 的审计推翻**：那些"折叠"目标其实是 **oracle 错选**
> （mdn search = 无障碍隐藏菜单 `a11y-menu`；mdn logo = 页脚 logo；
> wikipedia home = 正文 13000px 处的 "Main page" 内容链接）。
> 第 2 条（wikipedia login：hit 但点击超时）**不受影响，仍然成立**。

与 WinSim 对照：像素端到端 0.79 里包含检测+接地+点击的全部损失；
真站结构通道把这条链缩到 **pick → click 两级，且两级都在 0.85+**
（表级 0.95）。**"结构在那里"这句在 7 个真实站上成立，代价仍是
提取器工程费（v2/v3 的 213 行 JS）而不是可用性。**

**局限**：弹窗遮挡未构成样本（8 站加载时全屏 overlay = 0，headless/地区
无 cookie 横幅）；点击成功 ≠ 任务成功（本实验只量"点得到"，未验后续状态）；
跨域能力只在受控 harness 验证，真实站 organic 样本为 0。

## 3.8 端到端通道对照（struct vs pixel，`real_site_e2e.py`）

> 复现：`python experiments/web/real_site_e2e.py --quick` / 去掉 `--quick` 为全量
> 数据：`results/web/real_site_e2e_results.json`

§5 原高优项（REPORT §12 "WinSim → 真实站点" 的真站通道版）。协议：同一
6 站 × 4 任务、**同一关键词选择策略（keyword_pick）**，只换感知通道：

- **struct 臂**：v3 快照（DOM/无障碍名）→ keyword_pick → prepare/hit/locator 点击；
- **pixel 臂**：截图 → RapidOCR 文本框 ∪ cv2 几何框 → 同一 keyword_pick
  （tag 由几何猜：宽矮 → input）→ 页坐标 mouse.click；**选前不碰 DOM**
  （代码顺序保证：截图/OCR/选完才做快照，快照只用于评分）。

公平性（REPORT §12，P4 教训）：两臂共用同一 oracle（DOM `oracle_pick`），
oracle 只评分、绝不进像素选择；engage 语义对称 = correct ∧ 点击前最上层属于
oracle。有效试次 n_valid（oracle≥0）= 12/24，oracle 口径与 §2/§3.7 完全一致
（struct 全 24 试次的 found = 0.500，复现 §3.7）。

**漏斗（valid，12 试次/臂）**

| 级 | struct | pixel |
|---|---|---|
| found（感知里有 oracle 目标） | 12/12 = 1.000* | 9/12 = **0.750** |
| pick（关键词选中） | 12/12 = 1.000 | 7/12 = 0.583 |
| correct（选中 == oracle） | 8/12 = 0.667 | 5/12 = 0.417 |
| 机制级 | hit\|pick 11/12 = 0.917，click_ok 10/12 = 0.833 | click_ok\|pick 7/7 = **1.000** |
| **engage（端到端接地）** | **6/12 = 0.500** | **5/12 = 0.417** |

\* struct 的 found 按构造恒真（valid 即 found）；像素的发现率只能在 valid 上算
（无 oracle 无从评覆盖）。

**失败机制不在同一层**（valid 上的 reason 分布）

| 臂 | ok | wrong_target | no_pick | click_timeout | occluded |
|---|---|---|---|---|---|
| struct | 6 | **4** | 0 | 1 | 1 |
| pixel | 5 | 2 | **5** | 0 | 0 |

- struct 感知全中（hit 0.917），主要损失是**策略错选**（关键词选中非 oracle
  元素，严格评分算错）——瓶颈在选择策略，不在感知；
- pixel 一旦命名对，机制 100%（click_ok 7/7），主要损失是**命名层**
  （no_pick 5：logo 是图像无文本、home 无可见文本），外加 found 0.75 的检测覆盖；
- 两臂失败**部分不相关**：pypi search 是 pixel 对而 struct 错；
  wikipedia login 是 pixel 成而 struct click_timeout（§3.7 已知的动态可点性）。

**成本不对称**：结构快照中位 41.5 ms vs OCR 中位 **4695 ms（≈110×）**
（cv2 仅 5.3 ms；中位 24.5 个 OCR 框 + 118.5 个几何框）。

**结论（小样本，方向性）**

1. 真站端到端 struct 胜 pixel，但差距**薄**：0.500 vs 0.417 = **恰一个试次**
   （n_valid=12）——远小于 WinSim 受控环境的 1.00 vs 0.79；
2. 差距来自**不同层**：struct 输在策略（wrong_target），pixel 输在命名
   （no_pick/检测）。共享同一关键词策略后，像素通道的真实短板是
   "把名字从像素里读出来"——这正是 OCR/VLM 该补的位置；
3. 本 pixel 臂 = 经典 CV+OCR（非训练检测器、非 VLM），结论限定于
   "经典像素通道 vs 结构通道"，不外推到一切像素方法；
4. 严格 oracle 评分把功能等价的错选记为 wrong_target——两臂对称，不偏袒。

**局限**：n_valid=12（Δ=1 试次，不作强效应量）；4 任务都在首屏附近，
未测滚动后的发现；engage 仍是接地口径（点击成功 ≠ 任务完成，同 §3.7）。
独立复现与补充量见 §3.9（`real_site_pixel.py`，结论收敛）。

## 3.9 独立复现与像素通道的两个附加量（`real_site_pixel.py`）

> 数据：`results/web/real_site_pixel_results.json`

与 §3.8 并行的**独立实现**（同 6 站、同 oracle 口径，协议三点不同），
价值在复现 + 补测 §3.8 没有的两个量：

1. 指标按**视口内 oracle 条件化**（12 个有效 oracle 中视口内 9、视口外 3
   ——像素通道的硬约束，单列报告）；
2. 像素**双臂**：`ocr-kw`（整屏 OCR → 同款关键词规则，主臂）+
   `geom`（纯 cv2 几何先验，副臂）；
3. 截图/检测/OCR/快照/命中都在**同一页面状态**内完成，只对主臂点击；
   另测**坐标漂移**（OCR 耗时期间页面动画 → "过期坐标"）。

**结果（视口内 9 个 oracle）**

| 量 | ocr-kw | geom |
|---|---|---|
| 感知覆盖 | OCR 读到目标文本 7/9；cv2 框覆盖 5/9 | 同左（共用感知） |
| pick | 6/9 = 0.667 | 4/9 = 0.444 |
| pick == oracle | 4/6 | **1/4** |
| hit（选中框中心处最上层 == oracle） | 4/6 = 0.667（无漂移子集 3/5） | 1/4 = 0.25 |
| url 变化（效果级） | 3/6 = **0.50** | 0/4 |

- **端到端（engage 口径，对全 12 个 oracle）**：ocr-kw ≈ 4/12 = 0.333，
  与 §3.8 的 pixel 0.417 / struct 0.500 同一量级——两份独立实现收敛；
- **geom 纯几何先验基本失败**（是 oracle 仅 1/4，url 0/4）：没有文本，
  位置先验在现代站点上选不中目标——像素通道缺的不是定位而是**命名**
  （与 §3.8 的 no_pick 主导互相印证）；
- **坐标漂移（像素通道独有）**：OCR 中位 2.7 s 耗时期间 2/12 任务页面
  明显变化（灰度均差 > 1.5；全量漂移中位 0.0）——结构通道快照 29 ms
  根本没有这个窗口；
- 成本：cv2 检测 7.7 ms ≈ 结构快照 28.6 ms，OCR 2667 ms（≈93×）。

**与 §3.8 合并读**：三臂排成一条清晰的梯度——

| 臂 | engage（对有效 oracle） | 瓶颈 |
|---|---|---|
| struct（DOM 名） | 6/12 = 0.500 | 策略错选 |
| pixel-ocr（OCR 名） | 5/12 ≈ 4/12 = 0.417–0.333 | 命名（no_pick/覆盖） |
| pixel-geom（无文本） | 1/12 = 0.083 | 没有名字就选不中 |

**结构通道只比"OCR 命名"多约 1 个试次，但快 2 个数量级、
无漂移窗口、不受视口条件化限制。**"文本命名"才是像素侧的主瓶颈
（定位不是）——这与 REPORT 的主结论（瓶颈是恢复哪些信息，不是模型大小）
在真站上再次一致。

## 6. 像素端到端对照（`real_site_pixel.py`）—— 公平检测器之后

> 复现：`python experiments/web/real_site_pixel.py`（6 站 × 4 任务）
> 数据：`results/web/real_site_pixel_results.json`

**公平性设计**：像素臂只准看 `screenshot()`（1000×700 视口）；
两条选择通道都用**手工先验**（与 struct 侧的关键词先验对称）：
`ocr-kw`（rapidocr 整屏读文 → 复用**同一个关键词规则**，主臂）与
`geom`（经典 cv2 候选框 + 逐任务几何先验，副臂）；动作是坐标真点击；评估用 DOM oracle。
**指标按"视口内 oracle"条件化**（像素看不清视口外，单列报告）。

| 指标（6 站，oracle 12；视口内 9、视口外 3） | struct 侧（§3.7） | 像素·geom | **像素·ocr** |
|---|---|---|---|
| 目标在视口内 | 可滚动（found 12/24=0.500） | 9/12 | 9/12 |
| 检测覆盖 / 读出目标文本 | — | 5/9（检测框） | **7/9**（OCR 文本） |
| pick | 0.594 | 0.444（4/9） | **0.667**（6/9） |
| pick 就是 oracle | — | 1/4 | 4/6 |
| **hit \| pick** | **0.895** | 0.250（1/4） | **0.667**（4/6） |
| 点击后 URL 变化 | click_ok 0.842 | 0/4 | 3/6（弱信号） |
| 成本（中位） | 快照 **11.9 ms** | 检测 8 ms | **OCR 2667 ms（≈90× 快照）** |

**四条结论**

1. **像素通道的可行路径是 OCR**：`pick 0.667` 已略高于 struct 侧关键词（0.594），
   但 **hit 0.667 < 0.895**——"读出名字"能补回**可选择性**，补不回**可点性**。
2. **几何先验基本失败**（pick 的 3/4 不是 oracle）：名字是语义、跨站稳定；
   位置/尺寸先验跨站不稳定。这与 §3.5"瓶颈在命名"互为镜像。
3. **成本两笔账**：①OCR **2.7 s/页**（wikipedia 4.3 s、hn 6.6 s）≈ 结构快照的 **90×**；
   ②~~视口外 3/12（25%）目标像素臂完全不可达~~ ⚠️**此条已被 §7 审计推翻**：
   那 3 个"视口外"目标全是 **oracle 错选**（隐藏 a11y 菜单 / 页脚 logo / 正文深处链接），
   **不是**像素通道的 reach 折扣——本样本里没有"真·视口外目标"的证据。
   （像素臂的其它结论不变：OCR 补可选择性不补可点性、几何先验跨站失败、近白 UI 盲区。）
4. **近白扁平 UI 是经典 CV 的硬伤**：wikipedia 搜索框是"白底+放大镜图标"，
   边缘/连通域阈值都看不见它（检测覆盖 5/9 的缺口主要来自此类）；
   OCR 靠 placeholder 文本"Search"绕过了这个盲区——**文本是像素里最可靠的结构**。

**方法学两坑（自捕，如实记录）**
1. **首轮 det=1/7 是度量 artifact**：拿视口外的 oracle 去考视口内的检测器
   （oracle y=13079 / y=-320）→ 指标必须按 `oracle_in_view` 条件化。
2. **臂间污染**：先跑的一臂点击后页面已变，后一臂的命中测试跑在改动过的页面上
   （hit 全 0）→ 修：**先测两臂的 pick/hit（不点击），最后只点主臂**。
   （"OCR 延迟→坐标过期"假设被证伪：漂移中位 0.00，仅 2/12 任务有漂移。）

**局限**：视口内样本仅 9（6 站）；struct 侧口径来自不同站点集（24 任务，含 harness），
两边不是严格配对；URL 变化是弱结局信号（搜索框不导航）；
OCR 用的 rapidocr 未调参（公平但非最优）；geom 臂的先验是本项目手写的、只调过一轮。

## 7. 量具审计：把"状态折叠"拆成"真损失"与"oracle 错选"（`real_site_oracle_audit.py`）

> 复现：`python experiments/web/real_site_oracle_audit.py`
> 数据：`results/web/real_site_oracle_audit_results.json`

**起因（现场取证）**：§3.7 把 mdn 的 search/login 记为"折叠在头部之外"。
逐候选体检（父链 rect/overflow/clip）后发现：

| 案例 | 表面诊断（§3.7/§6） | **实际是什么** |
|---|---|---|
| mdn search | "折叠头，需先交互展开" | **无障碍隐藏菜单** `UL.a11y-menu`（高 0、y=−320，给屏幕阅读器的跳转链接） |
| mdn logo | "视口外不可达" | **页脚 logo**（y=2785；头部 logo 没被选中） |
| wikipedia home | "视口外不可达" | **正文 13000px 处的 "Main page" 内容链接**（header 里根本没有名字含 home 的元素） |

**审计口径**：对 24 个 (site×task) 槽位，把 v1 oracle 的候选逐个做"意图/可见性"体检——
不在隐藏容器（祖先链 height≈0 且 overflow hidden/clip）、在文档范围内、
home/logo 必须在头部区域（y<200 且不在 `<footer>` 内）、search 必须是 input/textarea/role=searchbox。

**结果**

| v1 分类 | 个数 | 说明 |
|---|---|---|
| ok | 7 | 合法目标 |
| **deep-content** | 1 | wikipedia home（正文链接） |
| **out-of-doc** | 1 | mdn search（a11y 隐藏菜单，y=−320） |
| **footer** | 1 | mdn logo（页脚） |
| not-a-searchbox | 2 | 名字命中但本体是容器（pypi 的 v2 能改判到真 input） |
| （无目标） | 12 | 该站本就没有匹配元素（任务定义的覆盖面问题） |

**三条结论**

1. **"状态折叠"是测量伪迹**：§3.7 的第 1 类损失（mdn，2 个 click_timeout）全部来自
   **oracle 错选**——隐藏 a11y 菜单在"名字匹配"下与真搜索框不可区分，
   而它在视口外、点击必然超时。**修正后：本样本没有"真·状态折叠"的证据。**
2. **真正的"动态可点性"损失仍然成立**：wikipedia login（hit=True 但 Playwright
   点击超时，sticky/稳定性）与 oracle 质量无关，是 §3.7 第 2 类，保持。
3. **量具要先审计**：这轮与 QGIS 线的教训同型（rect 溯源、伪迹 verifier）——
   **在真实站上，"任务定义 + oracle 规则"本身是最大的误差源**；
   §6 的"视口外 25% 像素不可达"也随之撤回（那 3 个目标都是伪迹）。

**遗留**：v2 过滤器偏严（24 槽位只有 8 个能通过），它是**审计器**不是替代 oracle；
要把 §3.6/§3.7 的全部数字重算，需要一个"意图标注"的任务集（人工确认每个 (站,任务) 的
真目标），那是扩站点实验的一部分。
