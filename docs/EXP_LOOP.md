# 经验闭环协议（EXP_LOOP）

> 目的：把「工程师改代码」换成「系统从自己的执行历史里生成经验，并用独立样本裁决」。
> 结果：`results/computer_use/exp_loop/EXP_LOOP_RESULTS.md`

## 1. 三层分离（本协议的核心）

| 层 | 内容 | 存在形式 | 谁能写 |
|---|---|---|---|
| 观察事实 | 动作、动作前后画面+文本、期望的可观测变化 | `episodes.jsonl` + `frames/*.png` | 采集器 |
| 经验假设 | 「这个量异常」的可测量判别式 | `detect.py` 的 detector + `hypotheses.json` | 归因器（只读 episode） |
| 验证规则 | 可执行的处置规则 + 指标 + 失效条件 | `rules.json`（status/metrics/gate） | 验证器（读标签，只在验证阶段） |

硬约束：

1. episode 里**不许出现原因字段**（"缝隙""描述文字"这类结论一律不写）。
2. 归因器**不许读** `labels.jsonl`。
3. 规则**不许**直接从假设变成生产行为：必须 val 半区过 gate，且生产代码里存在对应钩子。

## 2. 数据切分与门槛

- 切分：`crc32(episode_id) % 2` → train / val（确定性，跨轮稳定）。
- 阈值：只在 train 上网格搜索 `recall - FPR`。
- 门槛：val `recall ≥ 0.90`、`FPR ≤ 0.05`、`n_pos ≥ 2`、`n_neg ≥ 3`。
- 适用范围：每条规则声明 `applies(det, ep)`，只在适用样本上算指标
  （否则「OCR 空串」样本会污染「点击生效」规则的 recall 分母）。

## 3. 规则字段

```jsonc
{
  "rule_id": "R1_assert_effect",
  "version": 1,
  "status": "active",              // proposed | active | retired
  "statement": "…可执行的自然语言…",
  "condition": "action.type==click and expected.kind in {...}",
  "hook": "click_slot_verified / _step_duck",   // 生产代码里的执行点
  "params": {"thr": 0.5},
  "metrics": {"train": {...}, "val": {"recall": 1.0, "fpr": 0.0, "n_pos": 3, "n_neg": 4}},
  "gate": {"recall_min": 0.9, "fpr_max": 0.05},
  "invalidate_if": "持续动画使 frame_diff 长期高于阈值"
}
```

`invalidate_if` 是必需的：经验必须写明自己**什么时候会失效**，否则会变成新的教条。

## 4. 生产闸门

`duck_guard.py` 启动时：

```
读 rules.json → 只取 status == active
             → 用 EXP_HOOKS 检查执行点是否存在（globals 里有同名函数）
             → 全部满足才打「经验规则已生效」，否则打「缺少执行钩子，未生效」
```

这条闸门的意义：即使经验库被写坏（或被人手工改成 active），
代码侧也不会因为一条没有执行点的规则而"假装生效"。

## 5. 当前规则集（第一轮）

| 规则 | 假设 | val |
|---|---|---|
| R1_assert_effect | 动作后必须有可观测变化，否则判未生效 | R=1.0 / FPR=0 |
| R3_empty_is_not_absent | 识别空串必须回退第二通道，不得判"无内容" | R=1.0 / FPR=0 |
| R5_hit_icon_center | 落点必须在图标中心容差内 | R=1.0 / FPR=0 |
| R2_refetch_after_action | 文本未变 → 重新取证 | **淘汰**（FPR=0.5） |
| R4_labels_only | 可点目标必须是短标签 | **拒绝晋级**（val 无样本） |

## 6. 已知局限（必须写在协议里，不许含糊）

1. 现在的 5 个 detector 是**人类给的先验**；数据只决定"哪条成立"，
   没有决定"该看哪些量"。离"系统自学"还差这一步。
2. 生产侧还没做 A/B：验证集上的 recall/FPR 不等于线上失败率下降。
3. 样本量小（24 条），val 半区每条规则只有 3–4 个样本；结论是方向性的，不是统计显著的。
4. 机制标签（gap/sentence/ocr）由采集程序写入 `labels.jsonl`，
   归因不读，但"哪些机制值得回放"仍是人选的。

## 7. 下一轮

```
detector 合成（把"看哪、阈值、文本特征"放进搜索空间）
  → 生产 A/B（规则开/关，比静默失败率）
  → 经验过期与回归监控（FPR 回升 → retired）
```

## 8. 自动合成（第二轮）

人类只提供**特征族**，判别关系由搜索生成：

```
episode → features.py（30+ 维：区域像素差分 / 亮度能量 / 文本变化 / 几何 / 动作元信息）
        → synth.py 候选：单特征阈值（阈值取 train 分位点）+ 双子句合取
        → train 定阈值 / val 选规则（精度优先 + 边际覆盖）/ test 独立裁决
```

关键设计：

1. **只在残差上计分**：人类规则已覆盖的正样本不再参与自动规则的边际收益，
   否则系统会自动"重发现"人类已经写好的东西。
2. **采集元信息不得进特征**：`A_is_click` / `A_fast` 这类字段描述的是"我们怎么采的"，
   不是失败机制；放进去会立刻"发现"假规则（实测踩过）。
3. **标签由独立判定器给**：点击类要求「仍在鸭子页 + 选中格落在被点位置 ±0.022」，
   识别类要求「仅识别空 且 整页识别有字」。采集方式不决定标签。

## 9. 最大的教训：漂亮的指标可能是采样偏差

自动合成的第一条规则 `G_x >= 0.546`（点击偏右 = 高风险）在 test 上 22/22、fp=0。
但当前游戏状态下**挂锁全在右侧**，而"右侧合法点击"这种反例在数据里根本不存在。

我们专门去采反例来证伪，结果那批点击全部落在挂锁上——**反而加强了这条假规则**。

由此写进协议：

> 任何位置/页面类规则，必须先在"反例可能出现的状态"下采样，否则不许晋级。

配套两条硬规则：

- **页面身份与失败机制分离**：`T_len_b`（文本长度）这类量是"这是哪一页"的代理，
  不是失败机制；用它生成的规则即使指标漂亮，也只当"页面指纹"用，不进失败检测。
- **标签噪声要显式报告**：同一批 `good_click` 在不同批次里既有 positive 也有 negative，
  说明判定器存在时序抖动——需要多次采样取多数，否则规则学的是抖动。

## 10. 现在的自主发现率

```
自主发现率 = 自动发现且过 test、并覆盖人类漏掉正样本的新规则数
           / (该数 + 人类规则在 test 上成立的条数)
```

第二轮机械计算 **0.667**（2 条自动规则 / (2 + 1 条人类)），
但扣除混杂后**实质为 0**：两条自动规则一条是采集几何产物，一条是页面代理量。

这不是坏消息——**能自己发现"自己发现的规则不可信"，才算真的开始有了判断力。**

## 11. 主动证伪（第三轮）

模块：`experiments/computer_use/exp_loop/counterexample/`

```
hypothesis_parser   规则 → 隐含前提（positional / page_identity / geometry / text_change / visual_change）
coverage_analyzer   找薄弱环节：命中区间内有没有"成功样本"、阈值是否单侧
scenario_generator  按前提类型提反例场景规格（不是随机补样本）
scenario_executor   真实界面构造（逐个位置尝试并记录证据）
falsification       三态裁决：refuted / holds / insufficient
report              机制级去重 + 三个学习指标
```

**铁律**：场景必须在真实界面里构造并观测；构造不出来就报 `insufficient`，
并在理由里写明"试过哪些位置、卡在哪"，**绝不伪造反例**。

### 三个学习指标

| 指标 | 定义 | 注意 |
|---|---|---|
| Discovery Rate | 通过独立 test 的**机制**数（触发向量 Jaccard ≥0.9 视为同一机制） | 按机制算，不按规则条数，避免同机制换阈值重复计数 |
| Falsification Rate | 实际做过反例尝试的规则中被推翻的比例 | 早期高是好事：能推翻错误假设比多产规则更有价值 |
| Robust Discovery Rate | 通过反例测试 + 独立 test 后仍成立的机制比例 | **证据不足不算稳健**（没被检验 ≠ 检验通过） |

### 第一轮结果（2026-11-14）

```
Discovery        = 2
Falsification    = 1.0  (1/1 真实反例尝试被推翻)
Robust Discovery = 0.0
```

- `A_T_len_b`（长文本页 ⇒ 失败）被**真实反例推翻**：在同一类长文本页面上成功切换了子标签；
- `A_G_x`（点击偏右 ⇒ 高风险）判为 **insufficient**：可达位置只有 `0.678=缝隙`，
  再往右无路可走，无法构造"右侧合法对象"，因此不许晋级、也不许当成成立。

### 已知缺口

1. 证伪结论尚未自动回写 `auto_rules.json` 的 status（下一轮补）；
2. 反例场景模板仍按前提类型白名单（positional / page_identity），
   未登记的前提类型只报"暂无场景规格"；
3. 生产 A/B 仍未做。
