# DUCK 执行协议（P0）

> 目标：把 DUCK 作为 MioArgus 的**第二种执行环境**（视觉/OCR 适配器），而不是继续维护一个专用脚本。
> 本协议先于代码：任何执行动作必须满足「前置条件 → 动作授权 → 后置断言 → 失败恢复」四段式。

## 0. 硬性门禁

**在 P0/P1/P2 三项交付完成并通过门禁之前，禁止任何生产性点击。**

门禁文件：`results/computer_use/duck_gate_pass.json`

```json
{"passed": true, "page_accuracy": 0.99, "duck_recall": 0.96, "jitter_px": 1.8, "runs": 100}
```

`duck_guard.py` 启动时若该文件不存在或 `passed != true`，**直接退出**，不执行任何动作。

## 1. 风险等级与动作授权

| 等级 | 动作 | 授权条件 | 执行策略 |
|---|---|---|---|
| **L0** | 截图、OCR、模板匹配、连通域统计 | 无 | 自由执行，只读 |
| **L1** | 页面导航（市场/蛋/鸭子/GOOS/任务、go_home、ESC） | 当前页面已确认 + 导航锚点匹配分 ≥ 0.85 | 执行后断言落在目标页面，否则回主界面 |
| **L2** | 喂食（点气泡）、合并（蛋格拖拽） | 目标二次确认 + 价格/等级约束 + 后置断言 | 每次执行前重读目标；执行后只验局部 |
| **L3** | 购买商人蛋、付玉米繁殖、敲蛋、订阅 | 默认禁止；需配置显式开启 + 人工批准令牌 | 不自动执行 |
| **L4** | 未知区域点击、盲坐标 | **永久禁止** | 仅记录，不执行 |

约束落地位置：

- 单价上限 `feed_cap=200` 属于**执行引擎的硬约束**，不是任务脚本里的 `if`。
- 任何目标若「类型/等级/价格」三项中有一项未确认 → 记 `rejected`，不执行。

| `market` | `DUCKS` 或 `我的市场` | — |
| `task` | `Challenge Week` 或 `广告` | — |
| `event_halloween` | `HALLOWEEN` + (`CANDY PATH` 或 `GUARANTEED PRIZE`) | 点抽奖（L3） |
| `collection` | `SWEET HALLOWEEN` + `已收集` | — |
| `daily_reward` | `每日奖励` + `领取` | — |

### 鸭子页的真实结构（2026-11-12 更正）

之前一直误判：把底栏上方那排小图标当成「鸭子槽位行」，按比例或按分类去点。
实际上那排是**收藏/奖励进度条**（鸭群图标、升级箭头、皇冠、灰点、宝石、挂锁），点它只会
打开收藏页或 `BUY A SLOT FOR A NEW DUCK` 购买页，**点不出鸭子**。

真实结构：

| 区域 | 内容 | 可执行动作 |
|---|---|---|
| 中央大卡片 | 当前选中的鸭子（Lv/稀有度/喂食气泡/繁殖状态） | 读状态、点喂食 |
| 卡片左右边缘 | 相邻鸭子露出一角 | 点击可选中 |
| 卡片下方一排图标 | **收藏/奖励进度条** | 只读，不点 |
| 底部标签栏 | 市场 / 蛋 / 鸭子 / GOOS / 任务 | 导航 |

切换鸭子的唯一可靠方式：**横向快拖**（`drag (0.75,0.47) → (0.25,0.47)`），
每次切一只。因此遍历鸭子必须用「轮播遍历」，不能用「扫描图标行」。

每只鸭子的可能状态：`点击喂食 N` / `已准备好交配` / `繁殖进行中 请勿打扰` /
`鸭子正在出售` / `已准备好质押` / `这是一只新鸭子 给它安排一个槽位`（槽位不足）。

## 3. 动作规格（四段式）

每个动作必须声明：

```
action: feed
risk: L2
pre:    page == duck AND target.duck_index 已确认 AND target.price <= 200
auth:   price 由气泡 OCR 二次读取；与首次读取一致才授权
post:   气泡价格数值变化 OR 气泡消失（鸭子喂满）
fail:   回主界面，记 reason=target_lost / price_jump / page_changed
```

```
action: merge
risk: L2
pre:    page == egg AND src.cell 与 dst.cell 的 (type, level) 完全一致
auth:   两次独立读取一致（防 OCR 滞后）
post:   目标格等级 +1，或源格变空
fail:   记 reason=level_mismatch，不做第二次尝试
```

## 4. 感知流水线（每一步都要有可观测输出）

```
capture → page_classify → target_detect → target_identify → spatial_locate
        → authorize(risk) → execute → verify(local) → recovery
```

| 阶段 | 输出字段 | 用途 |
|---|---|---|
| capture | window_rect, timestamp, frame_hash | 复现与去重 |
| page_classify | page, confidence, anchors_hit | 页面识别准确率 |
| target_detect | boxes[], count | **目标发现率（召回）** |
| target_identify | type/level/price, confidence | **目标识别准确率** |
| spatial_locate | center, jitter_px | 位置稳定性 |
| authorize | allowed, risk, reason | **不确定目标的拒绝率** |
| verify | changed, evidence | 动作成功率 |

必须分开统计：`发现率`、`识别准确率`、`执行成功率`——否则换更好的视觉模型也无法归因。

## 5. 门禁协议（P0 验收）

**连续 100 次只读感知，零点击。** 每次采集：

| 指标 | 定义 | 通过线 |
|---|---|---|
| page_accuracy | 与人工标签一致的帧占比 | ≥ 99% |
| duck_recall | 检出彩色缩略图数 / 人工标注数 | ≥ 95% |
| position_jitter | 同一图标跨帧中心点标准差 | ≤ 3 px |
| state_change_accuracy | 计时器/队列读数变化与 OCR 文本变化一致率 | ≥ 98% |
| rejection_rate | 低置信目标被拒绝的比例 | 100% |
| unknown_page_rate | 判为 unknown 的帧占比 | ≤ 1% |

未达标 → 只允许 L0，禁止 L1 及以上。

## 6. 失败原因码（事件流必带）

```
page_unknown / page_mismatch / target_not_found / target_ambiguous
level_mismatch / price_jump / cap_exceeded / anchor_low_score
```

### 已发现的规则脆弱点

页面锚点曾因文案变更（`下一颗蛋及后续` → `自动合并`）导致 `unknown`，安全侧表现为“全部拒绝”。
结论：页面规则必须写成**多锚点容错**，且锚点失效时要能在事件流里看到 `page_unknown` 计数，而不是静默失败。

### 分类接受规则：用差距，不用绝对分（2026-11-12）

现象：执行侧 `duck_slots_vision` 返回 0，退化到盲扫，结果点开右侧锁槽的购买页。

根因：模板匹配对真实鸭子的分数是 **0.79**，对挂锁是 **0.96**；我用了 `score >= 0.85` 的绝对阈值，把鸭子全拒了。
正确做法是**比较类间差距**：

```python
cls == "duck" and duck >= 0.60 and (duck - padlock) >= 0.05
```

同时两处配套修正：
1. 槽位行改为**自适应定位**（0.58–0.78 内找图标最密的一行），不再写死带区；
2. 删除“按比例盲扫 18 格”的兜底——视觉失败就跳过本轮，宁可不做也不点锁槽。

回归验收（规则变更后重跑）：场景 A 24 槽、场景 B 26 槽，stability 1.0、duck_recall 1.0、padlock_as_duck 0.0，无退化。

### 舞台结算浮层（2026-11-12 修正）

`THROWED TOMATOES / HOORAY! YOU KICKED THEM OUT` 浮层**是可以关闭的**，右上角有 X。

之前的错误处理顺序是：点 X → 立刻复查（浮层还在退场动画中）→ 判定“关不掉”→ `Ctrl+R` 重载 → 服务端把浮层**重新推回来**，于是永久卡死。

正确顺序：
1. 先尝试关闭（点 X，最多 2 次，每次等 1.5 s 让退场动画结束）；
2. 关闭后再检查环境；
3. 只有两次都关不掉才重载；
4. `check_env` 必须在 `close_popup` **之后**执行，否则会把可关闭的浮层误判为环境阻塞。

### pyautogui failsafe 被下游模块重置（2026-11-12 修正）

症状：后台看护每轮都报 `PyAutoGUI fail-safe triggered`，喂食/合并整批失败，但人工跑同样代码正常。

根因是**导入顺序**：`duck_guard.py` 先 `pyautogui.FAILSAFE = False`，紧接着 `import bigemap_runner`，
而 `bigemap_runner.py` 在模块级写了 `pyautogui.FAILSAFE = True` —— 赋值被覆盖回 `True`。
人工跑时不觉得，是因为窗口不在角落、鼠标没落在 (2559,0)。

正确做法：
1. `FAILSAFE = False` 必须在**所有 import 之后**执行（封装成 `no_failsafe()`）；
2. `Game.click()` 与每次任务批次开头再重申一次，防止运行期被重新导入的模块改回；
3. 交付前用 `pyautogui.position()` 报出真实光标位置，并在角落位置做一次 `moveTo` 冒烟测试。

教训与「bubble-gone」「浮层关不掉」同源：**一次赋值不代表一直生效**，状态被谁覆盖要看导入链。

### 喂食循环的结束条件（2026-11-12）

`task_feed` 的单轮内循环必须区分三种结局，且**单只到顶不得结束整轮**：

| 结局 | 判据 | 行为 |
|---|---|---|
| 该只到顶 | `do_feed` 返回 `cap` | 记入 `capped` 跳过集 → 找下一只继续 |
| 没有可喂的 | 有槽位但都不可喂（`no-feedable`） | 本轮结束，允许进入合并 |
| 观测失败 | 整排槽位识别为空（`vision-miss`） | 本轮结束但**不切页**，合并推迟 |

反例（已修）：`if stopped == "cap": break` —— 第一只喂到 200 就退出，
其余鸭子整轮得不到喂食，表现为「明明还有没喂满的鸭子」。

### 喂食单价必须单独裁数字区（2026-11-12）

气泡实际内容是「点击喂食 🌽96」。**整条气泡直接 OCR 不可用**：玉米图标与数字贴在一起，
RapidOCR 稳定输出 `点击喂食%` 或 `点击喂食9%`，放大 1x/3x/5x、抹绿色都没有改善。

后果：单价 96 的鸭子被当成「没有喂食气泡」跳过，表现为「明明还有没喂满的鸭子」。

可行做法：

```python
FEED_BAND = (0.26, 0.545, 0.48, 0.115)   # 判「有没有气泡」
PRICE_BOX = (0.520, 0.595, 0.200, 0.045) # 只取玉米右侧数字区
# 数字区 4x 放大后 OCR：96 / 204 / 210 全部读对
```

即「气泡有无」与「单价数值」用两次不同的裁剪分别判定；数值读不出时记 `price-unread`
并跳过该鸭，**不允许在价格未知的情况下点击喂食**（会突破 200 上限）。

### 浮层卡死必须升级处理（2026-11-13）

一夜实测：舞台结算浮层（`THROWED TOMATOES` / `KICKED OUT`）连续 **11 轮**关不掉，
日志每轮只写一句「舞台浮层仍在，本轮放弃（不重载）」，`feeds=0`，整夜零产出。

原设计只考虑了「重载会重新触发浮层」，于是**永不升级**——这比误重载更糟。

现在的分级策略（`G.popup_fails` 计数）：

| 连续失败 | 动作 |
|---|---|
| 1–2 次 | 记录 `popup_stuck` 事件 |
| 每 3 次 | ESC + 点卡片外侧空白（绕过关闭键位置漂移） |
| ≥ 5 次 | 允许一次 `Ctrl+R` 重载（比卡死好） |

并且 `one_cycle` 在浮层未关闭时**清空 `_last_run`**，让下一轮 60 秒后立即重试，
不再按小时等。判据很简单：**任何「放弃」分支都必须在有限轮次内换成别的动作。**

### 爱心蛋：点鸭子卡片本体（2026-11-13）

用户确认的机制：**每只鸭子身上的爱心蛋，点鸭子卡片本体就收集**；
已经收过时再点会提示「暂无爱心蛋。稍后回来即可获得爱心蛋。」

因此 `collect_love` 不再依赖任何视觉标记，做法是「轮播遍历 + 每只点一下」：

```
for each duck:
    click(0.50, 0.47)        # 卡片本体，不是喂食气泡 (0.50, 0.62)
    if 面板里出现「领取/收取」: do_claim()   # 每日奖励 / 喂鸭大赛 也走这条路
    carousel_next()
```

两个附带发现：
1. 点鸭子有时弹出**每日奖励**面板（`领取` 按钮在 y≈0.84），原有 `do_claim` 只扫 0.42–0.92
   的窄带，正好漏掉它 → 扫描区间改为整块卡片 (0.03,0.10,0.94,0.86)。
2. 那排小图标**也是鸭子槽位**（点一下可切换鸭子），但左右两端混着升级/皇冠/挂锁，
   按坐标点容易点到 `BUY A SLOT`，所以仍以拖拽轮播为主。

### 槽位带是**可横向滚动**的；选中=高亮；必须走查而不是先扫后点（2026-11-14 关键修正）

这一条推翻了上面的「固定步长 0.265 + 0.0558*i 逐个点」：

- **槽位带会横向滚动**。点后面的槽位/点挂锁后整排会平移，固定坐标立刻失效
  （实测点 0.450 时行内变化发生在 0.486；扫描后按旧坐标点会落在两颗图标之间的缝隙里）。
- **选中的那一格图标会高亮**：亮度 V≈144~170，其余图标 V≈58~88。
  这是唯一可靠的「选中」信号——页面文字不可靠，因为点缝隙时卡片不变，
  读到的仍是上一只鸭子的内容。
- 图标行中心在 **y=0.699**（相对高度）。偏 4px（y=0.694）时高亮就测不出来，
  会得到「全是灰的、没有选中项」的假结论。
- 检测到的锚点要**按固定间距 0.056 补齐漏检格**：较暗的图标会被漏掉
  （实测 0.337 / 0.449 两颗漏检，于是「有 7 只只数到 5 只」）。

正确做法（`walk_ducks`，2026-11-14 用户给出、已实测通过）：

```
下一个锚点 = 当前高亮锚点 + 相邻槽距（槽距取本帧检测值，实测 ≈0.056）

每步都从**当前帧的高亮**重新起算 → 整排怎么滚动都不影响
```

不需要「先检测出下一颗图标」，也不需要任何绝对坐标。
实测步进：0.170 → 0.226 → 0.282 → 0.338 → 0.394 → 0.449 → 0.506 → 0.561 → 0.617，
每步都用「点完重新检测，选中格是否落在刚点的位置（同帧内 ±0.022）」校验。

再往右就进入「待分配新鸭」区（见下节）。

关键点：**扫描和动作必须在同一遍里完成**，不能「先扫描出清单，再按旧坐标逐个点」——
整排一滚动，旧坐标就全偏了（这也是喂食 `fed=0` 的直接原因）。

实测（2026-11-14 18:46，走查结果）：

```
1  x=0.170 COMMON   Lv5  已准备好质押
2  x=0.226 COMMON   Lv5  已准备好质押
3  x=0.282 COMMON   Lv5  已准备好质押
```

### 合并蛋：两个隐蔽缺陷（2026-11-14 修正）

**1. 白蛋被整片过滤掉**

```python

```

后果：板上一眼就能看到的 5 个白蛋**从来没进过扫描**，所以总报"没有可合并的同种蛋"。

```python

```

**2. 合并成功判定是假的**

### 合并算法优化（2026-11-14）

时序实测：拖动后 **0.2s 画面就稳定**（该外观计数 2→0 后不再变化），所以等待时间不是瓶颈。
真正的两个短板：

| 问题 | 修法 |
|---|---|
| 某一对没生效就 `break`，整轮中止 | 记进 `blocked` 集合，**继续试其它对**；成功后清空 blocked（局面已变） |
| 预算 3 次/轮，12 组只合 3 次，剩下等一小时 | 预算提到 **20**，一轮跑到收敛为止 |

等待也从 1.1s 降到 0.7s（实测 0.2s 就够）。

```

合并 (1,1)->(1,2)   3 → 0 个，结果等级 3
合并 (1,1)->(2,2)   3 → 0 个，结果等级 3
合并 (1,1)->(2,1)   2 → 0 个，结果等级 2

```

注意「3 → 0」：三颗同种一次合并会消耗两颗、剩一颗被新蛋顶掉，
所以判据用「减少」而不是「恰好减 1」。

### 一次失败的分组实验：按等级配对（2026-11-14，已回退）

> 同一款蛋在「可提交」状态会带绿底并被压暗，外观距离被拉到 12–16（超过阈值 8），


单轮 50 次"成功"，但等级在原地打转。根因：**蛋种库的等级是推断出来的**，


保留的改进：蛋种库（显示等级/学习新档）、稳定性双扫、优先最像的一对、失败不中止。

### 逐格枚举：锚点必须"每步重算"，且判定不能用卡片（2026-11-15 凌晨）

正确的算法（用户给的）：

```

```

今天把它改坏又改回来的四个根因，全部有实测：

1. **选区混入左右边缘伪高亮**
   - 最左 `x≈0.010` 的鸭群图标亮度能到 152，与真正的选中格（170）只差 18 → 选中判到索引 0/2 上，走查乱跳；
   - 最右 `x≈0.988` 有个恒定亮块（V≈128）：点 0.392 时选中格 V=132，margin 只有 4 → 判成"没有高亮"。
   - 修：选区限定 `0.15 < x < 0.96`，margin 门槛 25 → 12。

2. **用卡片当"有没有前进"的判据**
   - 三只 `Lv5 已准备好质押` 是**不同个体**，卡片完全一样 → 被判成重复，只记 1 只。
   - 修：前进判据 = **高亮换位置** 或 **卡片变化**；卡片相同不再是重复。

3. **锚点不跟随"不高亮的鸭子"**
   - `鸭子正在出售` / 无槽位新鸭 点了**卡片会换但高亮不动** → 锚点卡死。
   - 修：高亮没前进时，锚点退回"刚点的位置"。

4. **个别格子可点区域与图标中心偏移 5–10px**
